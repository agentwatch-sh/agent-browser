The relay serves a CDP endpoint for Playwright, the Playwright MCP and agent-browser's own commands.
Behind it the browser model answers the browser-level calls with C10 ops. It sends each page-level
call to `debugger.sendCommand` (two-modes design, sections 4 and 8). On Linux it answers one page
call itself: focus emulation (one window per page, below). This file is the master for C11. The
vectors: `test/vectors/endpoint.json`.

**The socket and the URL.**

- A Unix socket with mode 0600. The relay makes it at the path that the daemon gives it:
  `/run/user/<uid>/agentwatch/browser-cdp.sock` on Linux, `~/.cache/agentwatch/run/browser-cdp.sock`
  on the Mac. A path is at most 103 bytes. There is no TCP port. The endpoint has no TCP port; the MCP port
  of stage 1d is a separate port (the MCP path, below).
- The URL is `ws+unix://<socket path>:/devtools/browser/<scope>`. Playwright's `connectOverCDP` and
  the Playwright MCP (`PLAYWRIGHT_MCP_CDP_ENDPOINT`) take it as it is (measured). The URL contains no
  secret, with or without the peer check (the scope's session, below).
- `agentwatch browser endpoint` prints the URL, with the session's scope (below).
  `agentwatch browser env` prints `PLAYWRIGHT_MCP_CDP_ENDPOINT=<url>`, with no comment lines. With
  `browser.control: false` there is no relay and no socket.
- A scope matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. Every agentwatch session name matches it.
  agentwatch picks each session's scope at its launch (the session's name then) and keeps it for
  the session's life, with or without the peer check: a rename does not change it, and no two live
  sessions share one scope. `agentwatch browser endpoint` and `agentwatch browser env` print that
  scope, not the calling session's current name.
- Without the peer check, every process of the daemon's OS user that can open the socket may
  connect, with any scope, as with `agentwatch browser` today: the scope is advisory (agent-browser
  #14). With the peer check, a connection needs its process in the agentwatch session of its scope
  (the scope's session, below).

**Before the upgrade.** The relay serves only the WebSocket upgrade of
`GET /devtools/browser/<scope>` (the path: a query does not change it). Its other answers have a
`text/plain` body:

- Another path, or a scope that does not match: 404 `Not found. Connect a CDP client to /devtools/browser/<scope>.`
- A request with an `Origin` header: 403 `A web page cannot connect to the agent browser.`
- With the peer check, a peer that the relay cannot read (a read at the accept fails, gives no pid,
  or gives a uid other than the relay's; the scope's session, below): 403 `The agent browser cannot tell which program connects, so it refuses the connection.`
- With the peer check, a peer that is not in the session of its scope (the session check, below):
  403 `The agent browser admits a connection only from a program of the agentwatch session of its scope. This program (pid <pid>) is not in it: it is in another session, it was started outside agentwatch, or it left the session. If this session started or restarted just now, connect again in a few seconds.`
  `<pid>` is the peer's pid, as the relay read it at the accept.
- The relay is not ready: 503 with one of these bodies.
  - 503 `The agent browser is not ready: its extension is not connected.`
  - 503 `The agent browser is not ready: its extension has not confirmed the allowlist.`
  - 503 `The agent browser is not ready: its extension is too old for agent mode.`
  - 503 `The agent browser is not ready: the allowlist has session roots, but the relay was started without --peer-check.`
  - 503 `The agent browser is not ready: the relay cannot read the program of a connection.` (the
    relay's self-test failed: the scope's session, below)
- A scope with no list: 503 `The agent browser is not ready: the allowlist has no list for this scope.`
- The relay is ready while the link is up (C10 `link`), an `allowlist` line came after that,
  `bridge.info` answered with `bridge` 1 or more, and the steps of the link up (C10, "The daemon
  and the relay") are done: for today's relay steps 1, 3 and 4 (the detaches); in the per-scope
  build also step 2 (`bridge.tabScopes`) and the target ids of step 3. A receiver before stage 2
  answers `unknown op` to
  `bridge.info`: it is too old. The relay admits a connection of a scope while it is ready and the
  last `allowlist` line gives the scope a list (the scope's list, below). A scope whose list is
  empty is admitted; it can open `about:blank` only. So the endpoint fails closed: no connection
  before the extension confirmed the operator's lists (two-modes design, section 10; per-scope
  design, section 8.4).
- The order of the checks. The relay sends the answer of the first check that fails, at once:
  1. A request with an `Origin` header: its 403.
  2. A path or scope that does not match: the 404.
  3. With the peer check, the peer read (the relay's own read at the accept: the scope's session,
     below): a relay whose self-test failed gives its 503 (`the relay cannot read the program of a
     connection`); else a peer that it cannot read gets the peer's 403. Both come at once, also
     while the relay is not ready.
  4. The relay is not ready, in this order: the link is down (`its extension is not connected`);
     `bridge.info` answered `unknown op` or `bridge` below 1 (`its extension is too old for agent
     mode`); no `allowlist` line came since the link came up (`its extension has not confirmed the
     allowlist`); `bridge.info` has not answered yet, or the steps of the link up are not done
     (`its extension is not connected`); a relay
     without `--peer-check` whose last `allowlist` line has a `roots` field (`the allowlist has
     session roots, but the relay was started without --peer-check`).
  5. With the peer check, a scope that the last `allowlist` line does not name: the no-list 503. A
     just-launched session connects again.
  6. With the peer check, the session check (the scope's session, below): the peer is alive, and
     the walk from it reaches a root of the scope that counts; a walk that stops at any other root
     refuses. Only when the walk reaches no root, on Linux, may the peer's cgroup count: it must be
     in the pane's scope of a root of the scope. Else the session's 403.
  7. A scope with no list: the no-list 503. With the peer check, that is a named scope whose entry
     is `null` (also an entry that applies as `null`, C4) or names a list that is not in `lists`;
     without the peer check, also a scope that the line does not name while `default` gives no
     list. Also a scope that an `end_scope` ended and that no later line has named again (the
     refusal after `end_scope`, "When a connection ends"). With the peer check this refusal is
     step 7 too, after the session check: a process of another session gets the session's 403
     first, as for any scope with no list.
  8. A request that passes steps 1 to 7 and is no WebSocket upgrade (a plain HTTP request) is
     admitted by no check and gets no connection: the 404 of step 2. So a plain request gets the
     same checks in the same order as an upgrade, and the 404 only when the scope is admitted. A
     request with a method other than `GET` gets the 404 at step 2.

  The relay never holds an upgrade (the service holds one only for its start at a use, below), and no side retries for
  the client: the client gets the answer's text (agent-browser's `src/cdp.ts` passes the body on in its error), and the agent
  connects again. So a just-launched session, whose scope the daemon has not sent yet, gets the
  no-list 503 until an `allowlist` line names its scope. Step 5 shows whether a scope is named. A
  scope is a session's name at its launch, and `agentwatch session list` shows the session names
  anyway (the same names, unless a session was renamed). With the peer check too, the relay never
  asks the daemon during an upgrade: it reads the peer at the accept, and step 6 runs in its event
  loop (a walk reads at most 33 `stat` files, at about 66 µs for each new pid on taylor: at most
  about 2.3 ms; an agent is 2 to 4 hops below its pane). A session that is live at the deploy of
  the peer check gets its root in the daemon's first line after it, like any live session (the
  roots' life, below). The shared vector: `upgradeChecks` in `test/vectors/endpoint.json`.
- The start at a use (the service; board ab-v16.94.11; C12, the start and the stop by use). In the service, an upgrade
  that step 4 refuses with `its extension is not connected` or `its extension has not confirmed the allowlist`, of a
  scope of a session of C12's last `set_sessions` while `browser.control` is not `false`, goes to the service's start at a
  use. First the service makes steps 5 to 7 from its own snapshot, while Chrome is down, in their order: a scope that no
  confirm can name (a scope that two live sessions share) gets the no-list 503; the session check with the roots of the
  scope's sessions in `set_sessions` (a connection from the service's own pid passes only with a live ticket of its
  scope) gets the session's 403; a scope with no list gets the no-list 503. Each comes at once, with no wait and no
  start. A live session's scope that the next `set_scopes` leaves out only for the restart gate (a launch after the
  service's start) or for rule 2 (a name that ended while Chrome was off) passes step 5: only a push and its confirm,
  which need Chrome, name it. Only an upgrade that passes them waits: when Chrome does not run, the service starts Chrome
  and Xvfb (one start for all the upgrades that wait), and the upgrade waits until the service is ready and its line
  names the scope, at most 60 s in all (also the wait for a stop by use that runs, and the start). Then steps 1 to 8 run again, and the client gets their answer: the connection, or the 503 of that moment.
  - While the service stops Chrome for lack of use, step 4 gives `its extension is not connected`, so a new upgrade
    waits for the stop's end, then starts Chrome again.
  - A start at a use that fails gives each upgrade that waits for it 503 `The agent browser could not get ready:
    <reason>.`, where `<reason>` is the start's error text (C12's answer of `start`). For 10 s after it, an upgrade gets
    that 503 at once, with no new start. After a stop of the fail-closed watch, a use starts Chrome again at most once in
    60 s: in that time an upgrade gets the 503 of that moment at once.
  - No other answer waits: the Origin's 403, the 404, step 3's answers, an extension too old, the roots without
    `--peer-check`, a scope that no session of the last `set_sessions` has, `browser.control: false`, the no-list 503 and
    the session's 403 come at once, as above. The relay of the old path (`agent-browser relay`) never waits.
  - An upgrade whose client leaves while it waits gets no answer, and no connection opens for it. At the service's stop,
    the socket of each upgrade that waits closes.
  - An MCP session stays open over a stop by use: its next tool call starts Chrome at step 8 of the MCP path, and the
    MCP's browser connects again with a new ticket (the MCP inside the service, below).
- A client message is at most `MAX_REQUEST` bytes (C10). A longer one closes the connection (code
  1009). A command whose bridge request would be longer gets an error (the refusals, below).

**When a connection ends.**

- `Browser.close` ends that connection only. The agent browser keeps running. Close code
  1000, `Browser.close ends this connection; the agent browser keeps running`.
- `end_scope` (C10): the relay closes the scope's connections with
  1000, `The agentwatch session ended`, and removes the scope's tabs. From the `end_scope` on, the
  relay refuses each new connection of that scope with the no-list 503 (step 7), also over a link
  change, until a later `allowlist` line names the scope again: the scope's entry in `scopes`,
  also with a `null` entry (C4, rule 2: a later session of the same name). With choice 5 b, the
  line that drops the `null` entry (C4, rule 3) names the scope no more: without the peer check
  the `default` list then admits the scope again, and with the peer check step 5 gives it the
  no-list 503 (a scope that the line does not name has no list). So the ended session's processes
  cannot connect in the moment before the daemon's next line, also with a `default` list. The
  relay keeps this set of ended scopes in memory only. A relay restart between the `end_scope` and
  the daemon's next line loses it, and a line that still names the ended scope with a list would
  admit its processes again. So this is a limit of the relay and a rule for the daemon: the line
  that the daemon replays to a restarted relay must not name an ended scope with a list (a `null`
  entry is safe, and so is a line that has dropped the scope). The shared vector: `endScopes` in `test/vectors/endpoint.json`. An `end_scope` whose name is
  no scope of the relay (for example a name of the session other than its launch scope,
  `AGENTWATCH_SESSION_ID`; C4) does nothing. agentwatch writes no `end_scope` for a name that is the
  launch scope of another live session: a rename into a former name can make one session's alias
  another session's scope. In the per-scope build the receiver's sweep closes the scope's tabs too,
  at the daemon's next `set_scopes` (C5), also when no relay runs: the sweep is the guarantee,
  `end_scope` the fast path (C4, the tabs of a session that ended).
- The relay never closes the browser's last window. Today's relay (before part 2) keeps it itself,
  as this bullet says; in the per-scope build the receiver keeps it (the last sub-bullet). A tab
  closes by the relay's `tabs.remove` (`end_scope`, `Target.closeTarget`), or by a client's
  `Page.close` on a page session (Playwright's `page.close({ runBeforeUnload: true })`), which the
  relay sends to Chrome. Before each of them the relay sends `tabs.query` with `{}`. When the tab is
  the browser's only tab, it first opens an `about:blank` window that is not focused and in no
  scope, as C5's closing rule opens `about:blank` before it closes the browser's last window. The
  relay does one such query and close at a time, so two closes cannot each find the other's tab and
  together close the last window. `Page.close` answers before its tab closes, so the next query
  waits for the tab's `tabs.onRemoved`, at most 2 s (a `beforeunload` handler can keep the tab
  open); after an error of `Page.close` it does not wait. When the query or the new window fails,
  the relay does not close the tab: `end_scope` leaves it open, and `Target.closeTarget` and
  `Page.close` give the client the error. A page's own `window.close()` is outside the relay: Chrome
  closes that tab itself.
  - Measured (Chromium 156): an `end_scope` that removed the browser's only tab ended Chromium,
    exit 0 (board ab-v16.39). Two removals at once of the browser's only two tabs (two scopes end
    together) each read two tabs, opened no window, and ended Chromium (review-48 check X2b; live
    again in review-51, with the relay's queue removed). A client's `Page.close` of the only tab
    ended Chromium too (review-51).
  - Today's relay (before part 2, so with the ops of agent package 0.2.0) opens the window with
    `windows.create` and `[{"url":"about:blank","focused":false}]`. Its known gap (board
    ab-v16.43): a close that a `beforeunload` dialog holds past the wait (2 s for `Page.close`; the
    30 s deadline for `tabs.remove`, which opens the dialog too and ends only after it: measured,
    C10, removals and the last window) still counts as another tab at the next query, so a later
    accept of the dialog can close the last window. In the per-scope build the pending close and
    the receiver's close of C10 are the rules for it.
  - Today's relay sends a client's `Target.closeTarget` as `tabs.remove`, which runs the page's
    `beforeunload` handler, while Chrome's own `Target.closeTarget` does not (measured: review-17
    checks T1 and the probe of C10). So Playwright's `page.close()` with no `runBeforeUnload` opens
    the dialog of such a page. Playwright with no dialog listener accepts it itself (playwright-core
    1.64.1), and the tab closes after its handler ran. A client with a listener, for example the
    Playwright MCP, must answer the dialog; else the call waits 30 s and fails with the deadline's
    text (not measured). The per-scope build removes this difference: there `tabs.remove` is the
    receiver's close (C10), as Chrome's own command.
  - In the per-scope build `windows.create` needs a scope (C10), which would put the window into
    one. So there the receiver keeps the last window for every close that the relay asks for, and
    this bullet goes (part 2; the orphan-tabs design, board ab-v16.39, sections 7 and 13; board
    ab-v16.41). The relay sends `tabs.remove` for `end_scope` and `Target.closeTarget`, and a
    client's `Page.close` on a page session goes to Chrome as any page call
    (`debugger.sendCommand`). Both run in the receiver's removal queue, with its window rule and its
    pending closes (C10, removals and the last window). `tabs.remove` is the receiver's close there
    (`Target.closeTarget` through `chrome.debugger`: no `beforeunload`, as Chrome's own
    `Target.closeTarget`); only a client's `Page.close` runs the page's `beforeunload` handler. The
    relay keeps no query, window or queue of its own for them; `Target.closeTarget` and `Page.close`
    give the client the receiver's answer (an error of the window rule too). A `Page.close` on a
    child session (a frame or a worker) goes to Chrome as today, with no window rule.
- A link drop (C10 `link` down): every connection closes with
  1011, `The agent browser's link went down`. The model starts again at the next `link` up. In the
  per-scope build it starts with the tabs of the receiver's map (C10, the steps of the link up): a
  scope's tabs stay open over a link drop and over a relay restart, and a client of the scope that
  connects again sees them, free (`context.pages()` after `Target.setAutoAttach`). Its CDP sessions
  do not stay: the receiver's cleanup at a link change, or step 4 at a relay restart, detached the
  tabs (C10). Today's relay starts with no tab: a client that connects again sees none of the tabs
  of before (measured, board ab-v16.39).
- The relay stops: every connection closes with 1001, `The agent browser stopped`.
- At each `allowlist` line, the relay closes every connection of a scope that has no list any more,
  with 1008, `The allowlist has no list for this scope any more`. In the per-scope build, at a line
  whose `scopes` and `lists` are objects, it also drops from its model each tab of a scope that the
  line gives no list: the receiver's sweep has closed those tabs, or taken them out of their scope
  into its orphan set (C5), so a later session of the same name never sees one (C4). A tab that
  still waits for its `bridge.tabScope` (up to `TAB_SCOPE_WAIT_MS`) has no scope yet, and it stays.
  At a line whose `scopes` or `lists` is not an object it drops no tab: the receiver sweeps nothing
  then (C5).
- With the peer check, at each `allowlist` line, the relay closes every connection of a scope that
  still has a list (the same list or another one) but whose root that admitted it (its pid and
  start, by the walk or by its cgroup) is no longer one of the scope's roots that apply (also at a
  line with no `roots` field), with 1008, `The session of this scope has a new process: connect again.`
  That happens when the pane respawns (a restart, an account swap, a resume: the roots' life,
  below). A connection keeps its scope until it closes, the line drops the root that admitted it,
  or the scope ends: the check runs once, at the upgrade. The shared vector: `lineCloses` in
  `test/vectors/endpoint.json`.

**The scope, and one connection per tab.**

- A connection sees and attaches only the tabs of its scope. A tab joins a scope when a connection
  of that scope opens it (`Target.createTarget`: the relay names the scope in C10's `tabs.create`
  or `windows.create`), or when the receiver reports it (C10's `bridge.tabScope`: a popup takes its
  opener's scope, a replaced tab its old scope). The relay never puts a tab in a scope that the
  receiver did not report; its own `tabs.onReplaced` handling follows `bridge.tabScope` too. Every
  other tab is in no scope, and no connection sees it: the operator's tabs, the restore tab of an import, a tab that
  the receiver's map does not hold. An act tab of the sign-in act is in its caller's scope for the list rules, but no

**One window per page (board ab-v16.28).** On Linux the relay gives each page a window of its own,

- The window comes forward for input, on Linux only. An input that starts an action is one of these
  calls on a page session:

  - `Input.insertText`;
  - `Input.dispatchTouchEvent` with `"type":"touchStart"`;

  Before such an input goes to Chrome, the model activates its page, as a person's press does:
  1. It reads the tab (`tabs.get`). When the tab is not active (a popup tab that the site opened in
     the window is in front), it selects the tab (`tabs.update` with `{"active":true}`).
  2. It reads the window (`windows.get`). When the window does not have the focus, it focuses the
     window (`windows.update` with `{"focused":true}`).
  3. It sends the input (`debugger.sendCommand`).

  With the stage on (the input stage, below), on Linux with one window per page, the first move of a translated
  pointer action is an input that starts an action too. So the activation comes before the path, not only before the
  press, as a person brings a window forward before the hand moves in it. A translated pointer action is a path that
  the stage sends for a client's call, with its press and its release: a move, a click, a hover, a drag, the stage's
  own focus click, or the way to a wheel point. The activation decides, as for a press, whether the page comes
  forward. The stage's own focus click is an input that starts an action.
- The order and the limit. The tab's later calls for Chrome (`debugger.sendCommand`) wait behind
  that input, and reach Chrome in the client's order. The calls that the model answers go at once.
  With the stage on, a client's `Page.handleJavaScriptDialog` goes at once too: it never waits behind that input
  (the input stage, below).
  The model runs one activation at a time, for all connections: an activation starts when the
  activation before it and its input went to the bridge. When an activation does not end in 2 s,
  the input goes on. After the limit, that activation sends no `tabs.update` and no
  `windows.update`; one already sent still runs. When an activation fails, the relay logs the error,
  and the input goes on. Every other input (a move, a wheel event, a release, a key-up) needs no
  activation. On the Mac every input goes to Chrome at once. With the paths on, the activation has
  the steps and the limits of the pointer at an activation (below).
- The reason for the activation: on Linux Chrome raises a window for a press in it, but not for a
  key. A key into a window that does not have the focus gives its page the focus while another page
  keeps it.
- Playwright's focus call. `pressSequentially`, `press` and `type` on a locator first call
  Playwright's injected `focusNode` with a caret reset (Playwright 1.64.1). `focus` on a locator
  calls `focusNode` too, without the caret reset, and its window comes forward too. Playwright sends
  the text of its utility-script function as a string argument of `Runtime.callFunctionOn`. With the
  caret reset, `focusNode` moves the caret of an input to its start when `document.hasFocus()` is
  false. So without the activation, Playwright types at the start of a field whose window does not
  have the focus. The rule depends on Playwright's internal names `injected` and `focusNode`. If a
  later Playwright renames them, the caret moves to the start again, and nothing else changes.
- On Linux and on the Mac, `Target.activateTarget` only selects the tab in its window (`tabs.update`
  with `{"active":true}`). `Page.bringToFront` goes to Chrome, which selects the tab and focuses its
  window. On Linux the live test measured that `Page.bringToFront` focuses the page's window; it
  measured no tab switch. With the paths on (Linux), both go through the activation step (the pointer
  at an activation, below).
- A popup stays where the site opened it: a tab in the opener's window (`target=_blank`, or
  `window.open` with no features), or a window of its own. The relay never moves a tab to another

- Measured (taylor, Chromium 156 in Xvfb, chrome-extension main 7e36332, three runs on 2026-11-05;
  the live group `windows` of agent-browser PR #44): with Playwright's defaults, with `noDefaults`

- The pointer at an activation (board ab-v16.70; the relay builds it in board ab-v16.71). When a
  window comes forward, the X server gives its page a real pointer event, with no movement, at the X
  pointer, and CDP input never moves the X pointer. So, on Linux with one window per page, the relay
  has the daemon move the X pointer (C10, the daemon's own ops) along a person-shaped path, from the
  last point of the page under the pointer to the last point of the page that comes forward, before
  the window comes forward. It does this for every client. The agent pointer design (agent-browser
  `docs/superpowers/specs/2026-11-06-agent-pointer-move-design.md`, section 3) gives the reasons. An
  unexplained change is a pointer event whose position change from the page's last pointer event does
  not agree with its movement (`movementX`, `movementY`).
  - The paths are on, off or unknown. They are unknown until the first answer of the probe,
    `daemon.pointerAt`, which the relay sends at each link up. An answer turns them on, and gives `at`,
    the display's size and `views`. `unknown op`, `wrong display` and `not connected` (an older daemon)
    turn them off until the next link up, and `no display` for 60 s. `busy`, `too many moves`,
    `disconnected` and the relay's own timer leave them unknown, and the next step that needs them probes
    again. Each time the paths turn on, the front page is unknown. While the paths are off, the relay is
    exactly as the bullets above say: no geometry read, no wait, no catch-up and no path, and
    `Page.bringToFront` and `Target.activateTarget` go as above.
  - What the relay keeps, in memory. Each page's last point: the point that Chrome last saw in it. A
    client's `Input.dispatchMouseEvent` or `Input.dispatchDragEvent` on the tab's own session sets it
    when it is sent; a wheel event more than 2 px from it, a child session's pointer input and touch
    input make it unknown. With the stage on (the input stage, below), the events that the stage sent set it, not
    the client's points. The pointer's place `at`, from the daemon's answers: unknown at the
    relay's start, at a link change, and after a failed or killed path or the relay's timer. The front
    page, the page under the pointer: the page of the last activation step that made it the front page
    (by the rule of step 6, when step 7's raise succeeds), or a new tab that comes on top, with no raise (a new active tab
    that opens a window, or that becomes the active tab of the front page's window); unknown at the
    relay's start, at a link change, at its `tabs.onRemoved` or `tabs.onReplaced`, after failed reads
    of step 1, after a raise that reached its limit or that failed for an input or a
    `Page.bringToFront`, and after any client's `Browser.setWindowBounds` (below). The held buttons: a
    tab holds a CDP button from a `mousePressed` on any of its sessions, its own or a frame's (review-68
    B2), until Chrome answered a `mouseReleased` on any of them, or until the tab closes, the link
    changes, the client's connection closes, or the tab is detached; a frame's pointer input still
    makes the page's point unknown. Each page's kept geometry: its last usable geometry from the
    relay's own reads (below). Each page's cover mark: another page came on top of it.
    A new tab that comes on top also marks the old front page. The mark changes no last point.
    The relay marks the leaving page before the raise, even when no X path plays or `at` is T.
    A failed or late answer can still have raised the window.
    A raise with an unknown front page sets no cover mark.
  - The activation step, with the paths on, one step at a time for all connections.
    `Page.bringToFront` and `Target.activateTarget` go through it too: they wait for the chain and for
    their tab's gate, as an input does, and answer after the step.
    1. Read the tab and its window (`tabs.get`, `windows.get`). When the reads fail or reach their
       limit, the front page is unknown and no path plays: the input goes with no raise, the
       client's `Page.bringToFront` goes, and `Target.activateTarget` sends its `tabs.update` within
       one `ACTIVATE_MAX_MS` (review-68 N3).
    2. Decide. With the front page known, a page comes under the pointer when it is not the front
       page, or, for `Target.activateTarget`, when its tab is not active and its window is the front
       page's window. The front page decides, not the focus, and for an input the raise (step 7) sends `windows.update` with `{"focused":true}` also to a focused window. With the front page unknown,
       the focus decides as above, and no path plays. Then a page becomes the front page (and step 6
       records it) only when the raise brings a window forward: the `windows.update` of an input whose
       window does not have the focus, or the client's `Page.bringToFront` (review-68 N1). A raise that
       only switches the tab (`tabs.update`, also that of `Target.activateTarget`), or an input whose
       window has the focus, leaves the front page unknown, with no record: a focused window can lie
       under a newer window. A path
       can play when a page comes under the pointer and the relay knows both last points: S of the
       front page and T of the page that comes forward.
    3. Wait and hold, only when a path can play, all within one `ACTIVATE_MAX_MS = 2000`; at the
       limit, no path. When the front page holds a button, wait for its release. The rule "no path
       when its tab's next call waits in the activation chain (its gate is set, or becomes set
       during the wait)" applies only while the front page holds a button, because only then does
       the release wait behind this step (the lead's decision in board ab-v16.71). No other page's
       button counts. Wait for the end of a catch-up that runs in the front page. Then chain the
       front page's gate on its old gate, so that its later calls wait behind the step in order.
       Last, wait for the answers of both pages' pointer input that already went to Chrome.
    4. Plan. Read both geometries (below) and, when it is unknown, `at`. No path when S or T is
       outside the front page's content box (its viewport less its scrollbars, 2 px inside its
       edges; the lead's decision in board ab-v16.71); none is needed when `at` is T. The path
       follows agent-browser's `src/input.ts` generator from S to T, sampled every 16 ms, each point
       clamped 2 px inside the front page's content box, in whole pixels (a page gets no mouse event
       over its scrollbars, so a path over one gave an unexplained change live), each `dt` at most
       250 ms, stretched in time until no step is over 50 px, with a first step of 2 px or more; when
       S is T and `at` is not, a short out-and-back of 2 to 4 px. No path when it does not fit C10's
       limits.
    5. Play: send `daemon.movePointer`, and wait for its answer, at most its wait.
    6. Record (the X records). On `ok` the answered position is the last point of both pages. With
       no path because `at` is T:
       T. On `pointer moved` the answered position is `at` and the entering page's last point, and
       the front page's point is unknown. After a failed path (`no display`, `not now` after a kill,
       the relay's timer), and in each other step that brings a page under the pointer with no path,
       the relay reads the pointer (`daemon.pointerAt`) and records it as `at` and as the entering
       page's point, and after a failed path also as the front page's point; a failed read leaves
       them unknown. Each record that maps a display position into a page gives that page an unknown
       point when the position is outside the page's viewport, or when the page's geometry is missing
       or not usable (the read's own rules, and no device-metrics override). The entering page is the
       front page when the raise (step 7) succeeds and either a page came under the pointer (the front
       page was known) or, with the front page unknown, the raise brought a window forward (step 7; the
       rule of step 2); a failed `tabs.update` of `Target.activateTarget` gives the client the error
       and keeps the front page as it was.
    7. The raise: bring the page forward, within one `ACTIVATE_MAX_MS`. For an input, `tabs.update`
       with `{"active":true}` when its tab is not active, and `windows.update` with `{"focused":true}`
       when a page comes under the pointer or its window does not have the focus; the client's
       `Page.bringToFront`; or the `tabs.update` of `Target.activateTarget`. The raise succeeds when
       its calls answer with no error within the limit. Then open the front page's gate.
    8. The input goes. A press's catch-up, if any, runs inside its chain step, from step 6's record.

    The limits: one `ACTIVATE_MAX_MS` for steps 1 and 2, one for step 3, 1.2 s for the reads of
    step 4 (the geometry's `GEOMETRY_WAIT_MS = 200`, and `daemon.pointerAt`), the path's wait (at most
    3 s), 1.2 s for the read after a failed path, and one `ACTIVATE_MAX_MS` for step 7 (after it, no
    `tabs.update` and no `windows.update`, as above). The worst case is about 11.4 s; the normal case
    is the path's time (0.3 to 1.5 s) plus some 30 to 60 ms.

    A client's `Browser.setWindowBounds`, with the paths on, waits in the activation chain (review-68
    B3): behind every step already in the chain (the path of the step that runs plays at the window's
    old place), and behind the catch-ups that run in its window's pages; then the front page is
    unknown, the kept geometry of every page in the relay's model goes (of every window and every
    scope), and the window changes. Later steps wait behind it. The window's scope check runs first: a
    call whose window holds no tab of the client's scope gets `Browser window not found` and changes
    nothing. With the paths off or unknown it goes at once.

    the relay first sends CDP
    `mouseMoved` events (no button) along a path of the same generator from the recorded point to the
    event's point, with C10's path limits (else no catch-up), each point clamped 2 px inside the page's

    A navigation can commit between the native lookup and the forwarded client call, or between
    world creation and the geometry evaluate.
    These separate CDP commands are not atomic: retention closes the cache-restore gap between
    geometry reads, but the navigation races and object-id format dependency remain.
  - The kept geometry (the lead's decision in board ab-v16.71; review-68 N2). The relay keeps each
    page's last usable geometry from its own reads. It keeps a read only when the read is usable as a
    front page's geometry: the rules above, not hidden, and not minimized when step 1 read the window.
    A read keeps or drops the kept geometry only when it answers within `GEOMETRY_WAIT_MS` and no drop
    event of the page (below) came after the read started (the relay counts each page's drop events):
    then a read that is not usable, or that fails, drops the kept one. A late answer is dropped and
    changes nothing. A catch-up's own read changes no kept geometry. Step 4
    uses it for a page that is no bridge tab (agent-browser's CLI ends its connection after each
    command, and the relay then detaches its page), and the catch-up uses it before a read. The relay
    drops it at every window event that it sees: any client's `Browser.setWindowBounds`; on the
    page's own session, a client's `Emulation.setDeviceMetricsOverride`,
    `Emulation.clearDeviceMetricsOverride`, `Emulation.setVisibleSize`, `Emulation.setPageScaleFactor`,
    `Emulation.setScrollbarsHidden`, `Page.setDeviceMetricsOverride` or
    `Page.clearDeviceMetricsOverride`; the page's `Page.frameResized`; its `tabs.onReplaced` (the new
    tab has none) and its `tabs.onRemoved`; and a link change. When a page that is no bridge tab has
    no kept geometry, the step sends no path. A front page whose `document.visibilityState` is
    `"hidden"` has no usable geometry (a page under the pointer is visible), so the step sends no path.
    The limit (review-68 N9): a kept geometry can be out of date when its window moves or changes its
    size, or its content box changes, with no event that the relay sees: a site popup's
    `window.moveTo` or `window.resizeTo`, the page's own fullscreen change, or a scrollbar that the
    page got or lost after the read (with no client attached, no `Page.frameResized` reaches the
    relay). The path then follows the old rectangle: real moves and hovers only, at points from the
    pages' input, at most 5 paths a second, over what lies there now. On the agent browser's Xvfb only
    the relay and the receiver place windows.
  - When the relay sends no path, that activation is as with the paths off: the paths are off or unknown;
    the front page, a last point or `at` is unknown (the first activation after the relay's start, after
    a link change, and after the paths turn on); a geometry is missing or not usable (a hidden front
    page has no usable geometry); S or T is outside the front page's content box; the path does not fit
    the limits; step 3 found a gate or reached its limit; or the daemon refused. A page that never had
    a pointer event then enters with its first pointer event, which is no position change. A page whose
    point was known or became unknown enters at the X pointer: at most one unexplained change or one
    jump. The entry carries the movement from the page's last point when Chrome still has that point
    as the base of the movement (the page got pointer input since its window last lost the pointer),
    so it is a jump when the X pointer is more than 100 px from that point (measured in board
    ab-v16.71: a press held 3 s, whose step ended at its limit with no path, gave the entering page a
    jump of 304 px). With an older daemon (`unknown op`, `not connected`) the paths stay off. On the Mac
    the relay sends no pointer op (`daemon.pointerAt` or `daemon.movePointer`).
  - Movement 0 after a page loses the pointer (measured in board ab-v16.71; fixed for known raises
    by board ab-v16.76): Chrome gives the covered page's next event movement 0. The cover mark now
    applies the catch-up even when its point is a client point. The same thresholds, path limits, held-button
    rule and per-tab bound of 4 unanswered catch-up moves apply. An unknown point still has no catch-up.
    A window change that the relay cannot observe remains outside this rule.

**The input stage (board ab-t30.6).** The input design is agent-browser
`docs/superpowers/specs/2026-11-10-vanilla-playwright-human-input-design.md` (board ab-t30.6). The operator answered its
questions Q1 to Q4 on 2026-11-10 with option a each (its section 15; board item ab-0z5). The operator answered its open
points 1 and 2 on 2026-11-12 (board item ab-pf8): a field with a sign that it opens a panel at a click gets no focus
click, and the typed keys of a `fill` stay (the focus click and the typing rule, below). The stage is a part of the
model (`src/relay/stage.ts`), between the tab's gate and the bridge. It keeps what each client call asks for: the point,
the button, the keys, the text and the element to scroll to. It changes how the call reaches the page: a person's path
from the page's last point, a pause, a press of a person's length, keys with a person's holds and gaps, a real Shift
key, and wheel notches. The vectors: `test/vectors/stage.json`.

- The build switch. Board tasks ab-t30.9 to ab-t30.12 build the stage behind a build switch. The switch stays off until
  all four tasks are merged, so that no part of the stage reaches a client before the whole stage is built. While the
  switch is off, the model sends each call as the rest of this file says, and no rule of this part applies. In this file,
  "with the stage on" names a rule that applies only while the switch is on.
- Every client. With the stage on, the stage shapes the input of every client of agent mode on every site, on Linux and
  on the Mac: Playwright, the Playwright MCP inside the service, and agent-browser's own commands over the endpoint (the
  answer Q1 a). No client sets anything. This part adds no op to C10 or C12, and no setting of the operator.
- The source. The stage sends CDP input (`Input.*` through `debugger.sendCommand`) on every platform. Real X input stays
  only for the X pointer's path at an activation (the pointer at an activation, above). On the Mac the stage uses no X
  input and never the operator's own pointer. The stage's own commands go as the model sends a client's: a press, or a
  move with a button down, that has no `force` gets `force` 0.5, and a command that reaches C10's timeout detaches the
  tab (where each call goes, above).
- The calls that the stage takes. On a page session of a tab (the tab's own session), the stage takes these calls:
  - `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent` and `Input.insertText`, of every `type`;
  - `Input.dispatchDragEvent` while a drag of the stage runs (the drag, below);
  - `DOM.scrollIntoViewIfNeeded` and `DOM.setFileInputFiles`;
  - each utility call that a recognizer matches (the recognizers, below).

  It passes every other call as the rest of this file says. On a child session of a cross-origin frame, the stage takes
  only `DOM.scrollIntoViewIfNeeded` and the utility calls of the hit-target, focus and fill recognizers. Playwright sends
  the input of a frame on the top page's session, and the stage plays it there. A same-origin frame has no session of
  its own: its utility calls come on the top page's session.
- The gate. The stage is a step of the tab's gate. A tab's calls reach Chrome in the client's order: a call that comes
  after an input call waits until the stage has sent the events of that input. So a `Runtime.evaluate` after a click
  sees the page after the click. An ordinary call that the stage passes leaves the gate when the model sends it, not
  when Chrome answers (above). The stage's own reads (an element's box, the focused element, a hit test, a frame's
  offset, a scroll position) go to Chrome inside the step, and no client sees them or their answers. They run in the
  relay's own isolated world (the geometry read, above), or they are protocol reads (`DOM.getContentQuads`,
  `DOM.getBoxModel`, `Page.getLayoutMetrics`, `DOM.getFrameOwner`, `Target.getTargetInfo`,
  `DOMDebugger.getEventListeners`, `DOM.getNodeForLocation`, `DOM.describeNode`, `DOM.resolveNode`). These reads start
  from the node handle of a client's call, and they run in Playwright's utility world on that handle: the frame mapping,
  the focus click's read of the field, its hit test and its reads of the area near the field, the typing rule's reads of
  the focused element in a cross-origin frame (on a node of that frame that a client's call named), the scroll's read of
  the element and its levels, the wheel point's rules 1, 3 and 4, and the recovery's read at the hit point. Four reads
  run in other worlds: the scroll's read and the wheel point's rules 1, 3 and 4 on a cross-origin frame's owner run in
  the relay's own isolated world on the owner (`DOM.resolveNode` with its `backendNodeId`), `mouseWheel`'s column (the
  scroll and the wheel, below) runs in the relay's own isolated world at the page's last point, and the wheel point's
  rule 2 and the focus click's read of the field's listeners read the listeners on handles of the page's main world
  (`DOM.describeNode` and `DOM.resolveNode`, then `DOMDebugger.getEventListeners`), which run no page script.
- The input lock. The agent browser has one input lock for all its pages, in memory (board ab-v16.46). A translated
  action holds the lock from its first event to its last. It takes the lock before its activation step, so that no
  window comes forward while the action of another page runs. A pointer action is its path, its press and its release. A
  key run is the keys of one tab with no other call between them: it ends at the tab's next call that is not a key, or
  1 s after its last key. A key that a client holds down, a modifier or not, keeps the action and its lock until the
  key's `keyUp`, as a held button does, within the limit `STAGE_ACTION_MAX_MS`, which counts from the action's start
  (board ab-t30.10, the open point N10 of board ab-t30.17). The tab's next call that is not a key still ends the key
  run, and it goes in the same action. The 1 s counts from the run's last key event when the client holds no key.
  Playwright's focus call, its focus click (when it gets one) and the keys or the text that follow it are one action:
  one lock, one activation and one limit, from the focus call. So are the call of `fill` that takes the lock (its field
  is a text field that fails the first focus test of the focus click, below), its focus click (when it gets one) and the
  text that follows it. With no key after it, such an action holds the lock until 1 s (`RUN_IDLE_MS`) after the call, or
  until the tab's next call that is not a key. Another tab's input waits for the lock, in the order of arrival, and that
  tab's later calls wait behind it in its own gate. In the service, agent-browser's own commands reach Chrome through
  the endpoint and the stage, so they share the lock. The file lock `input.lock` stays only for agent-browser's direct
  mode (its own Chrome, with no endpoint). A hold has the limit `STAGE_ACTION_MAX_MS = 25000`: at the limit the plan
  ends (dialogs, below), so the lock is free at once, the rest of the action goes with no person's timing, and the stage
  logs it. At this limit the stage sends no release of a client's button or key: the client still holds it, and its own
  release goes later. The stage takes the lock again in the order of arrival, with the same limit, as the events of an
  ended plan do (dialogs, below), and then sends the planned releases of a key run (a release that it answered early)
  and the release of each key of its own (its Shift, the modifier of a chord that the stage sends, such as the Control
  of `Control+Home`, and a key of a typed text). The lock that an ended plan's events take again (dialogs, below) has
  the same limit: at the limit it is free, and the plan's remaining ended calls go with no lock and no activation.
- The answers.
  - A held answer. The stage answers a client call only after it has sent the events of that call and Chrome has
    answered them:
    - a move, after the last move of its path;
    - a press, after the pause and the press;
    - a release, after the hold and the release;
    - a wheel call, after its last notch;
    - a key press, after the key's `keyDown`.

    Playwright sends the move, the press and the release of a click together, so the release arrives before the press
    has its answer. The stage keeps their order.
  - The early answer of a key release. Rollover needs the next key's press before this key's release, and Playwright
    waits for the answer of each key call. So the stage answers a `keyUp` before it sends it when the plan says that the
    next key can overlap: the base part of the next interval (the interval less the part of the letter pair) is shorter
    than this key's hold. The release then goes at its planned time. Every later call of the tab that is not a key press
    waits until that release has gone.
  - In no other case does the stage answer a call before its events. A client can trust an answer: the page has the
    events.
  - An error of an event. When Chrome refuses an event of a plan, the stage stops the plan and sends no more of its
    events. First it sends the release of each button and key that the plan holds. The client call of the refused event
    gets Chrome's error, and each other client call of the plan whose events did not go gets the same error. A sample that
    the stage sends before a hit-target setup (the hover's samples outside the target, the recovery's move out) belongs
    to no client call that has come: at its error the plan stops in the same way, and the setup goes as the client sent
    it, with no path of the stage's before it (no hover path).
  - Shift and rollover. A key with no Shift that follows a shifted key waits for the planned release of that key and for
    the release of Shift. The stage never sends a release before its planned hold has passed.
- Dialogs (the input design, section 4.3a). A page with an open dialog answers no input event, and the stage waits for
  the answers of its own events.
  - A client's `Page.handleJavaScriptDialog` never waits. With the stage on, the model sends it to Chrome at once, before
    the tab's gate and before any step of the stage, of an activation or of a world lookup. A client sends that call only
    after `Page.javascriptDialogOpening`, so it expects no call of its own to go first.
  - A dialog ends the plan. The stage watches the tab's `Page.javascriptDialogOpening` events that go to the client. When
    a dialog opens during a plan, the plan ends at once:
    1. The stage drops the events of the plan that no client call asked for (the rest of the path, the pauses).
    2. It frees the input lock at once.
    3. When the dialog closes, it takes the input lock again, in the order of arrival, and it runs the activation before
       an ended press or key press (the window comes forward for input, above).
    4. It sends at once, in order, each event that a client call of the plan asked for and that has not gone (the move
       to the client's point, the press, the release), and the release of each button and key that the plan holds, with
       the `clickCount` of its press. Then it frees the lock, and only then does it open the tab's gate.

    Chrome keeps the input events that it got before the dialog opened, and it drops each input event that it gets while
    the dialog is open: it answers that event at once, and the page never gets it (measured by board ab-t30.9 on Chromium
    156: a release and a move sent while the `confirm()` of a `mousedown` handler was open were answered at once and never
    reached the page, and the press that opened the dialog was answered after the close). So the stage holds the events
    of an ended plan until the close, and the page gets what Playwright's own input gives it. The stage never goes on with
    a plan after its dialog closes, and the tab's later calls wait in its gate behind those events, so no event of a plan
    goes after a later client call. Every end of a plan (a dialog, `STAGE_EVENT_WAIT_MS`, `STAGE_ACTION_MAX_MS`) follows
    these steps; only at a dialog do steps 3 and 4 wait for the close, and at `STAGE_ACTION_MAX_MS` step 4 sends no
    release of its own (the input lock, above).
  - The end of the wait for a close: `Page.javascriptDialogClosed`; Chrome's answer to the client's
    `Page.handleJavaScriptDialog`; the client's `Page.disable` (no `Page.javascriptDialogClosed` can come after it);
    `Inspector.targetCrashed`; a navigation of the tab's main frame (`Page.frameNavigated` with no parent); and the end of
    the tab in the model (a drop). At the first four the steps above go on: the stage sends the held events, and each
    held client call gets Chrome's answer, or Chrome's error. At the others:
    - A navigation of the main frame. The stage sends no held move, press or key press, so none reaches the new
      document. Each held client call gets the error that the context is gone. Step 4 sends only the release of each
      button and key that the plan holds, with the `clickCount` of its press, so nothing stays down. Then the lock is
      free, and the gate opens.
    - The end of the client's session or connection (also a C10 timeout's detach, which ends the client's sessions of
      the tab, and the end of the relay's link, which closes every connection). The stage sends no held event, and
      nothing goes back to the client. It sends only the release of each button and key that the plan holds, with the
      `clickCount` of its press, at once, before the model detaches the tab. The lock is free at once, and the gate
      opens.
    - The tab's end (its target ends, the tab closes, or Chrome detaches it). The lock is free at once. Each held client
      call goes to Chrome as the client sent it, with no lock, and gets Chrome's answer, or Chrome's error for a closed
      target. Then the stage sends the release of each button and key that the plan holds, and the gate opens.

    A drop ends the plan also when no dialog is open. Each held call of a dropped tab ends on the tab's old state, also
    when its step runs after the drop, so no lock stays with a dropped tab.
  - Each client call of an ended plan gets Chrome's own answer to its event when that answer comes, or Chrome's error.
    The stage gives no answer of its own, except the error at a navigation of the main frame (above).
  - Each read of the stage waits at most `GEOMETRY_WAIT_MS` (200 ms). At the limit the read fails open: the stage sends
    the client's call as it is, and counts it.
  - Each wait for an answer of the stage's own event has the limit `STAGE_EVENT_WAIT_MS = 2000`, counted from the oldest
    event of the plan that has no answer. At the limit the plan ends as at a dialog. This also covers a dialog when no
    client has `Page` enabled, and a dialog between two events of a plan. A late answer changes nothing. With no
    `Page.javascriptDialogOpening` the stage knows of no dialog, and it sends the events of the ended plan with no wait
    for a close.
  - A hold counts from the send of the press, not from its answer, so a `confirm()` in a `mousedown` handler does not
    make the hold longer. When the answer of the press does not come, the plan ends by these rules, and the release goes
    by the steps above: after the dialog's close, or with no wait for a close when the stage knows of no dialog.
- The timestamps and the rate.
  - Each event that the stage sends has a CDP `timestamp` that is a person's input latency before its send:
    `(Date.now() - latency) / 1000` on Linux, in whole milliseconds, as X11 gives the times of its events. The latency is
    `STAGE_LATENCY_MS` = 3 to 5 (ms, a first value). The time comes from the send, never from the plan, so no event has
    a time in the future. On the Mac the timestamp keeps its fraction:
    `(performance.timeOrigin + performance.now() - latency) / 1000`.
  - Pointer moves go at the rate of a device: one move each `STAGE_MOVE_MS = 8` ms (125 Hz, a first value). The stage
    sends each move at its time, with no wait for the answer of the move before it. Chromium then puts the moves of one
    frame into one `pointermove` with their samples, as for a real mouse.
  - At most `STAGE_MOVES_IN_FLIGHT = 8` moves of a tab are without an answer. When a move is due while 8 wait, the stage
    stops the path, sends the client's own event, and logs it. For the stage's paths this bound takes the place of
    `CATCH_UP_MAX_UNANSWERED`.
  - On Linux the stage rounds each point to a whole CSS px, as X11 gives its points. Playwright's points can have a
    fraction.
- A person's input (first values). The generator (`src/human/`) draws each value with a seed, from the parameter files
  `src/human/params/linux.json` and `mac.json`. A reviewed change of a parameter file changes these values, this part
  and the vectors together. Each scope gets one person, drawn once for the life of the scope, so that a site cannot link
  two sessions by one rhythm.
  - A path starts at the page's last point, never at a fixed point. When the page has no last point, the path starts at
    the X pointer's place mapped into the page (Linux, at an activation), else at a random point of the middle 30% to
    70% of the viewport.
  - A path has one sample each `STAGE_MOVE_MS`, in whole px on Linux, with no sample that does not move, at a speed of at
    most 3.5 px/ms. It ends at the client's point, or at the spread point of its press (below). Its time is 300 to 1000
    ms (Fitts's law). When a long move cannot keep both rules, the speed rule wins: the path takes longer than 1000 ms,
    and its time has no upper bound. A move of more than 500 px can add an overshoot leg only while its time stays at
    most 1500 ms.
  - The pause before a press is 80 to 400 ms. The press has `force` 0.5 and a hold of 60 to 180 ms. The gap of a double
    click, from the first release to the second press, is 90 to 150 ms.
  - The hold of a key is 50 to 250 ms. A Shift `rawKeyDown` comes 45 to 95 ms before a shifted character, which then has
    `modifiers` 8, and the release of Shift comes 15 to 60 ms after the release of the last key that it holds. A run of
    shifted characters keeps Shift down.
  - In a chord, each modifier comes 40 to 120 ms before the key, and the releases come 20 to 80 ms apart, in reverse
    order. A client's later modifier of one chord (for example the Shift of `Control+Shift+ArrowLeft`) comes 20 to 80 ms
    after the one before, and less when that keeps all of them within 80 ms of the first, so that the key comes 40 to
    120 ms after each.
  - A wheel notch is `STAGE_NOTCH_PX = 120` px on Linux (the notch of X11), and the gaps between notches are 35 to 90 ms.
  - No idle moves: the pointer moves only for a client's call (the answer Q4 a).
- The pointer: `Input.dispatchMouseEvent`.
  - `mouseMoved` with no button down, to the page's last point: no event, because a mouse that does not move sends none.
    The stage answers it at once, with no lock and no activation.
  - `mouseMoved` with no button down, at most 50 px from the page's last point: samples of the client's line at the
    rate of the device. Their speed is 0.5 to 1.5 px/ms, with 0 to 1 px of jitter across the line. Such a move is a step
    of `mouse.move` with `steps` or of `click({ steps })`, or a short move.
  - `mouseMoved` with no button down, farther: a path from the page's last point to the client's point.
  - A hover (a hit-target setup with the action `hover`, below). When the stage sees the setup, it plans the whole path
    to Playwright's point, sends the samples of the path that are outside the target's box, and then sends the setup. It
    sends the rest of the path, from its first sample inside the box, at Playwright's `mouseMoved`. When the pointer is
    inside the target's box already, the whole path goes after the setup. With `hover({ modifiers })` the modifier's
    press goes as the client sends it, and the last leg has the client's `modifiers`. The hover's action holds the input
    lock from its first sample to its last. When Playwright's `mouseMoved` does not come within 1 s of the answer of the
    setup, the stage drops the rest of the path and frees the lock, and it does so at once after a miss of the setup.
  - `mousePressed`: a pause when the press follows a path, then the press, with the client's `button`, `buttons`,
    `clickCount` and `modifiers`, and `force` 0.5. The press is at the client's point rounded to a whole px, or at the
    spread point (below). A press with `clickCount` 2 or 3 comes one gap of a double click after the release before it.
    A press away from the page's last point (a client that sent no move there) gets a path there first, and then the
    pause.
  - `mouseReleased`: the release, at the later of its arrival and the send of the press plus the hold. So a client's
    `delay` gives a hold of at least that delay. The release of a button that the stage released at the end of a plan
    (dialogs, above) gets no event, because a button that is up cannot go up: the stage answers it at once. The same
    holds for the `keyUp` of such a key.
  - The spread point. A person's press spreads around the middle of a target: an offset from the middle with a standard
    deviation of 1/8 of the target's smaller side, at most 1/4 of that side. The path then ends at the spread point. The
    stage uses it only when all of these are true; else it presses at the client's point, rounded:
    1. a locator click: a hit-target setup of the action `mouse` before it, `clickCount` 1, and no press of the same
       action with `clickCount` 2 or 3 (so never a press of a `dblclick` or of a triple click);
    2. no `position`: the client's point is within 1 px of the middle of the element's content quad (the answer of the
       client's own `DOM.getContentQuads`);
    3. an element whose effect does not depend on the point: `button`, `a[href]`, an `input` of the type `button`,
       `submit`, `reset`, `checkbox` or `radio`, `label`, `summary`, or an element with the role `button`, `link`,
       `checkbox`, `radio`, `tab`, `menuitem` or `switch`; never a `canvas`, an `img` with a map, an `svg`, a `video`, an
       `input` of another type, a `textarea` or a contenteditable;
    4. the stage's own hit test at the spread point gives the same element as at the client's point.

    The stage decides the spread point when it plans the path to the client's point. So a press that comes after the
    answer of that move (a click with `delay`) and a click in a frame (whose hit-target setup gives the hit point in the
    frame's own points) are at the client's point, rounded.
  - A click with a modifier (Playwright's `ensureModifiers`). The modifier's `rawKeyDown` goes as it comes, because
    Playwright waits for its answer before the move. The path and the press have the client's `modifiers`. The stage
    holds the modifier's `keyUp` until 60 to 200 ms after the mouse release, and answers it after it has gone. When the
    pointer is at the client's point already (no path), the press comes 40 to 120 ms after the modifier's press, the time
    of a chord.
  - A click or a hover in a frame. The client's input comes on the top page's session, in the top page's points, and the
    stage plays it there. The hit point of a hover's setup in a frame is in the frame's own points, and the stage maps it
    to the top page (the frame mapping, below).
  - `Input.dispatchTouchEvent` and `Input.synthesizeTapGesture` go as they are. Playwright refuses `tap()` without
    `hasTouch`, and a context from `connectOverCDP` has none.
- The drag.
  - `mouseMoved` with the left button down while the client's `Input.setInterceptDrags` is on (Playwright's drag manager:
    `dragTo`, and `mouse.move` with a held button over an HTML5 draggable). The stage first waits 100 to 300 ms after the
    press, as a person does. Then it sends a short path with the button down, until Chrome reports
    `Input.dragIntercepted`. It sends the rest of the path to the client's point as `Input.dispatchDragEvent`: first a
    `dragEnter` of its own at the first point after the report (with the data of `Input.dragIntercepted`), then
    `dragOver` events at the rate of the device. When Chrome reports no drag, the whole path goes with the button down.
  - A client's `Input.dispatchDragEvent` in a drag of the stage: a `dragEnter` goes as a `dragOver` at its point, because
    the page has its `dragenter` already. A `dragOver` goes as a path of `dragOver` events to its point. A `drop` goes
    after a pause, as a press does. A `dragCancel` goes as it is.
  - A drag event of a drag that the stage did not start goes as it is.
- The keys and the text: `Input.dispatchKeyEvent` and `Input.insertText`.
  - A key run (`keyboard.type`, `pressSequentially`, `type`, `press`, `keyboard.down` and `keyboard.up`): each key gets
    a person's timing. That is the hold, the time from one press to the next with its pauses at the ends of words and
    lines, and rollover by the early answer. A key press goes at the later of its arrival and its planned time. A
    release goes at the later of its arrival and the end of the key's planned hold. So a client's `delay` gives a hold
    of at least that delay.
  - A shifted character that comes with `modifiers` 0 (Playwright's capital or symbol): a Shift `rawKeyDown` before it,
    the key with `modifiers` 8, and the release of Shift after it. In about 70% of cases the left Shift (`location` 1)
    comes for a key of the right hand, and the right Shift (`location` 2) for a key of the left hand.
  - A chord of `press` (for example `Control+A`): the client's modifier presses, the key and the releases in reverse
    order, with the times of a chord above. A key that comes with the Shift bit while no Shift key is down gets the same
    Shift press. A client's own press of Shift while the stage's Shift is down sends no event, because the key is down;
    the client's later release is the release of that Shift, with that Shift's own code (its side), also after
    `STAGE_ACTION_MAX_MS` and at an ended plan, and it sends no event when the end of a plan released that Shift
    already. The Shift is then the client's, and the stage sends no release of its own for it. When the client releases
    it before the stage's shifted characters end, the next shifted character gets a new Shift press of the stage's. A
    bit of `Control`, `Alt` or `Meta` that a client sets while it holds no such key goes on the event as it is, with no
    press of the stage's own. A press of a key that is down already (a second `keyDown` with no `keyUp` between) is a
    keyboard's auto-repeat: it goes at its arrival with `autoRepeat` true, with no new hold. A `char` goes right after
    its key's press.
  - `Input.insertText` (Playwright's `fill`, `keyboard.insertText`, and a character with no US key in `keyboard.type`):
    typed keys when the typing rule (below) allows them. Else the text goes as it is, after one person's time from one
    press to the next. The first typed key replaces the selection that Playwright's script made.
  - `clear()` (Playwright's script selects all, then the `Delete` key): the key with a person's hold.
  - The typing rule. The stage sends typed keys in place of the text of an `Input.insertText` only when all of these are
    true; else it sends the call as it is:
    1. The focused element (the stage's own read at the call; when the focus is in a cross-origin frame, the stage
       reads it on that frame's own session) is an `input` of a text type (`text`, `search`, `email`,
       `url`, `tel`, `password`, `number`, or no type) or a `textarea`. A contenteditable keeps the inserted text,
       because the editor of a page can change typed keys.
    2. The text is not empty, each character has a key on the US layout (`src/record.ts` `charKey`), and the text has no
       line feed and no tab. A line feed would send a message in a chat field with Enter-to-send, and a tab moves the
       focus.
    3. The plan at the person's speed fits in `STAGE_TYPE_MAX_MS = 10000`, or the plan at the fast end of the person's
       spread (100 to 120 ms a key) fits in it, and then the stage types at that speed. A longer text goes as one
       `Input.insertText` (the answer Q2 a).
    4. On the Mac the same, with the Mac's editing commands for keys such as Backspace (`src/human/keys.ts`
       `macCommands`).
    5. The client holds no key: a held Shift, Control, Alt or Meta would change the typed keys, and a held letter would
       go down twice.

    Typed keys follow the times of the plan that rule 3 checked, so the typed text takes at most `STAGE_TYPE_MAX_MS`.
    The call is answered after the plan's last event. After the last key the stage reads the value of the field. When it
    is not the field's text before the keys with the typed text in place of its selection (after `fill`, whose script
    selects all of it: the text), the stage logs it, with no text, and counts it, and it does not repair the field. This
    is the one named exception to the same result as Playwright's own input: a key handler of a page (a tag input, an
    autocomplete, an input mask) can act on typed keys, where Playwright's own `fill` inserts the text in one step. When
    a plan of typed keys ends before its last event (a dialog, `STAGE_EVENT_WAIT_MS`, `STAGE_ACTION_MAX_MS`, or a
    navigation of the main frame), each character whose `keyDown` the stage sent is typed, except at a dialog: Chrome
    drops each input event that it gets while a dialog is open, so there a `keyDown` sent after the first event of the
    plan that has no answer at the end did not reach the page. At `STAGE_EVENT_WAIT_MS` and at `STAGE_ACTION_MAX_MS` the
    page can be busy (a key handler that runs long): Chrome queues its input events and gives them to it later, so the
    stage first waits for Chrome's answers of the plan's sent events, with the lock free, for at most one more
    `STAGE_EVENT_WAIT_MS`. When the answers do not come in that time (a key handler that never returns), no character of
    the rest goes, because a key with no answer can still reach the page later. The release of each key that the plan
    holds goes as at any end of a plan, with no wait for its answer: Chrome gives it to the page when the page answers
    again (when the client's session ends during the wait, the release goes at that end). The call gets the error `The
    input stage ended a typed text at <the end>, and <n> characters may not have gone: the page did not answer.`, where
    `<n>` counts the characters whose `keyDown` has no answer from Chrome. After the dialog's close, with the lock taken
    again in the order of arrival (and, when characters remain, the activation, because another tab's action can take
    the window's focus while the lock is free), the stage sends the release of each key that the plan holds. Then, when
    the field that the typing rule's read marked (a value of the world of that read, which no page script sees) still
    has the focus by the focus click's test (it is the active element of its document, and that document has the focus),
    the stage sends the characters that were not typed as one `Input.insertText`, as the client's own call, which gets
    Chrome's answer. Else, and at a navigation of the main frame, no character goes, and the call gets the error `The
    input stage ended a typed text at <the end>, and <n> characters did not go: <the field no longer has the focus, or
    the page navigated>.` after Chrome's answers of the plan's events and of its releases, or after
    `STAGE_EVENT_WAIT_MS` when they do not come. When every character was typed, the call gets its answer after Chrome's
    answers of the plan's events.
  - The time of a key run. The stage does not know the length of a run in advance. It types at the person's speed for
    the first `STAGE_RUN_SLOW_MS = 12000` of the run, then at the fast end of the person's spread. At
    `STAGE_ACTION_MAX_MS` the rest of the run goes at Playwright's own speed, with no person's timing, and the stage
    counts it. So a `pressSequentially` or a `type` of more than about 850 characters still ends with Playwright's 30 s
    timeout through the stage (measured by board ab-t30.18: 820 to 921 characters went within 30 s, and on a busy box
    once only 598), and the rest of its text does not go. This is the state until board task ab-t30.19, which builds the
    operator's answer on board item ab-8fu (2026-11-12): "can we do a simulated copy/paste for long text input? and we
    use a person typing for short input only?" The stage's build switch stays off until that task is merged.
- The focus click. Before Playwright's script focus of a text field (the focus and fill recognizers, below), the stage
  clicks the field as a person does, by the rules of `src/input.ts` `focusField`.
  - The stage reads the field in Playwright's utility world on the node's own handle: whether it has the focus, its
    kind, the length of its text, and its caret. A field with the focus gets no click. Before Playwright's focus call
    the stage takes the lock and runs the activation (the window comes forward for input, above); the field then has the
    focus when it is the active element of its document and that document has the focus (Playwright's own test). Before
    `fill` the stage reads the field before the activation: when it has the focus by the same test, the stage gives no
    click and runs no activation; else the stage takes the lock, runs the activation and reads the field again. The
    field of `fill` is Playwright's retarget of the node (the control of a label). A field that is disabled or read-only
    gets no click (Playwright's `fill` refuses it, and a script focus of a disabled field does nothing), and the stage
    counts it.
  - Only a text field gets the click: an `input` of a text type, a `textarea` or a contenteditable. On another element
    the utility call passes (the answer Q3 a).
  - A field with a sign that it opens a panel at a click gets no click (the operator's answer on board item ab-pf8,
    2026-11-12). After the focus test (before `fill`, after the activation and the read again), the stage reads the
    field's signs: in its read of the field, the role `combobox` (a token of the field's `role`, or of the `role` of an
    element around it in the flat tree), `aria-haspopup` with the value `true`, `menu`, `listbox`, `tree`, `grid` or
    `dialog`, `aria-expanded` with the value `true` or `false`, `aria-autocomplete` with the value `list` or `both`, and
    an `input` whose `list` names a `datalist`; then, on an `input` only, a `click` listener of the page's own scripts
    on the field itself whose handler is not an empty function in one of the forms of `EMPTY_HANDLER`
    (`src/relay/stage.ts`: `function name(…) {}`, `(…) => {}` and `e => {}`, each also `async`, with only white space in
    the body), which it reads on the field's handle in the page's main world, as the wheel point's rule 2 reads them,
    with the stage's object group, so that Chrome gives the text of each handler. A listener of another event is no
    sign: a page can count the presses of a field with a `mousedown` listener, and such a field can open nothing. A
    `textarea` and a contenteditable have no listener sign, because an editor puts a `click` listener on its own root;
    the cover count (below) measures a panel that a click on such a field opens. An empty handler is no sign either,
    because a framework can put one on an element whose click its root handles; a listener whose handler Chrome does not
    give is a sign. Playwright's script focus then goes as the client sent it, as with Playwright's own input, and no
    click opens a panel (a field that opens at focus still opens, as with Playwright's own input). The page sees a focus
    with no click on such a field, also when its click listener opens nothing. Such a field gets no notches either,
    because the script focus scrolls it into view. The stage counts it, with its sign. When the read of the listeners
    fails or does not end within `GEOMETRY_WAIT_MS` in all, the field gets no click, and the stage counts it.
  - After each focus click the stage counts the new elements that cover the area near the field: the field's box widened
    by 40 px on each side and by 240 px above and below it, within the viewport of its own document. Before the path to
    the click, it reads every element at each point of a grid of 9 columns by 25 rows over that area
    (`elementsFromPoint`), and two frames after the release it reads the top element at each point. An element there
    that was at no point before, and that is not the field, an element inside it or an element around it, is new. It
    counts once, with its highest ancestor that was at no point before (a panel with its cells). The count measures the
    panels that the signs above miss, as an upper bound: a hint that the focus shows, a hover panel that the path
    opened, other changes of the page during the path, and a field node that a framework replaces at the focus count
    too. The stage sends no input of its own for them (no `Escape`, no other click).
  - The click goes where the script focus puts the caret. In an `input` or a `textarea` with text, and in a
    contenteditable, the point is 2 to 5 px from the left edge (Playwright's caret reset puts the caret at 0). In an
    empty `input` or `textarea`, it is a point from 25% to 75% across. The point is 35% to 65% down in an `input`, and 6
    to 12 px from the top in a `textarea` or a contenteditable. The script focus puts the caret at the start of an
    `input` with the caret reset (`pressSequentially`, `press` and `type`), and else where the field's own selection is
    (a `textarea`, and `focus()`). When the caret is not there after the click, the stage sends keys of its own that
    move it: to the start `Home` (an `input`) or `Control+Home` (a `textarea`), to the end `End` or `Control+End`, and to
    another place in a text of at most 64 characters the start, then `ArrowRight` and `Shift+ArrowRight`. Else the stage
    sets it with the field's own `setSelectionRange` in Playwright's utility world, and counts it. On the Mac the keys
    are `Meta+ArrowLeft` (an `input`) or `Meta+ArrowUp` (a `textarea`) to the start and `Meta+ArrowRight` or
    `Meta+ArrowDown` to the end, with the Mac's editing commands of each key with its modifiers (`src/human/keys.ts`
    `macCommands`: `Meta+ArrowRight` is `moveToRightEndOfLine`). `fill` gets no caret keys, because its script selects
    the text. Before Playwright's focus call, an `input` of the type `email` or `number` with text gets no click: its
    caret cannot be read or set, and the script focus leaves it where the field's own selection is. The utility call
    alone gives it the focus, and the stage counts it.
  - A field out of view first gets notches into view (the scroll, below), also inside a frame's own scroller; then the
    stage reads the field again and clicks it. These notches are for the focus click of `fill` and of Playwright's focus
    call (`pressSequentially`, `type` and `press`); board ab-t30.12 decides the other clicks of this part
    (`selectText()`, the file chooser, a `select`, a date input). When the notches cannot bring it into view, and on the
    Mac until the Mac's wheel model exists, the field gets no click, and the stage counts it. A point of the click
    outside the visible part of the field's nearest scroller gets no click, and the stage counts it.
  - A field that has no box, or that another element covers at the point of the click, gets no click. The stage's own
    hit test reads the element at the point in the field's own document, and at each frame level above it the element at
    the mapped point: in a same-origin level in Playwright's utility world, and in a cross-origin level with
    `DOM.getNodeForLocation` on the parent's session, against the frame owner's `backendNodeId`.
    `DOM.getNodeForLocation` reads a point of the parent's document, so the stage adds the scroll of that document to
    the mapped point (its layout viewport's offset, from `Page.getLayoutMetrics` on the parent's session), and it gives
    no click when it cannot read that scroll. Each must be the field or the frame's owner. The utility call alone gives
    it the focus, and the stage counts it.
  - A field in a cross-origin frame: the stage maps the point of the click to the top page (the frame mapping, below),
    and it sends the click on the top page's session.
  - `selectText()` on an `input` or a `textarea`: a click on it and the select-all chord (`Control+A`, on the Mac
    `Meta+A`), then the utility call.
- The scroll and the wheel.
  - `mouseWheel` on Linux: notches of `STAGE_NOTCH_PX` in the direction of the call, on each axis, at the page's last
    point, with a person's gaps. The stage keeps a residual for each axis of a page: what the page's wheel calls asked
    for, less what its notches gave. A navigation of the main frame starts the residual again. A call gets `n = max(0,
    round((|delta| + r) / 120))` notches (round half up), where `r` is the residual in the direction of the call. When
    `n` is 0 and `r` is 0 or more, the call gets one notch, so a call whose delta is not 0 gets a wheel event unless
    earlier notches have already given it. So a series of wheel calls scrolls the asked total within one notch.
    Playwright's `mouse.wheel` does not wait for the scroll and does not check it. A call that earlier notches have
    given gets no event: the stage answers it at once, with no lock and no activation. A call whose delta is 0 on both
    axes gets one wheel event with that delta at the client's point, as Playwright's own input sends it. The notches of
    the vertical axis go first. The first notch of a call comes after the call's column read (below), at the later of
    that read's end and one gap after the page's last notch or the end of the stage's path before it, so the calls of a
    client that sends them at once get a person's gaps too. When the page has no last point, the stage first sends a
    path to the client's point, as before a press, and the notches go there. The stage sends each notch at its time with
    no wait for the answer of the one before, as a wheel sends its events. Before the notches, the stage reads the
    call's column from the page's last point, in the relay's own isolated world: the content that the notches move under
    the point, on the scroller that the point's chain scrolls first in the direction of the call, as rules 1, 2 and 4 of
    the wheel point (below) read it, also inside open shadow roots and in the elements assigned to their slots. The
    element under the point at the start, the elements around it, the elements inside it when it is an element of rule
    1, and the elements with `position: fixed` do not count. When the column meets such an element, the notches go until
    the next one would bring it under the point, and the rest goes as one wheel event at the same point, one gap later,
    in the same action, and the stage counts it. The residual does not change, and the stage answers the call after
    Chrome answers that event. Over a cross-origin frame, and when a read fails, all the notches go, and the stage
    counts it. When the plan of a call ends before its last event (dialogs, above), a notch is gone when Chrome answered
    it, and at a dialog also the first notch with no answer at the end (it opened the dialog), but no later one (Chrome
    drops the input that it gets while a dialog is open). At `STAGE_EVENT_WAIT_MS` and at `STAGE_ACTION_MAX_MS` the
    stage first waits for the answers, for at most one more `STAGE_EVENT_WAIT_MS`; when they do not come, the call gets
    an error with the count of the notches that may not have gone. The notches that did not go go as one wheel event
    with their sum, at the page's last point, as the client's own event of an ended plan, only when the page's last
    point is still a wheel point of the call's scroller: after a dialog's close, with the lock taken again, the stage
    reads the column again; the scroller of each axis must be the same, the element under the point must be the same or
    have a chain up to that scroller that passes rule 1, and the column must hold no element of rules 1, 2 and 4. Else
    no rest goes, and the call gets an error that names the end and the count of the notches that did not go. A
    navigation of the main frame from the start of the column read stops the notches of a call, as it stops a typed
    text: no rest goes, and the call gets that error.
  - `DOM.scrollIntoViewIfNeeded` (Playwright's scroll before each pointer action, and `scrollIntoViewIfNeeded()`), on
    Linux:
    1. The stage reads the element's box (the call's `rect` in it, when the call has one) with its scroll-margin, and
       its levels, innermost first, up through its same-origin frames in the flat tree (a slotted element's slot comes
       before its parent), in Playwright's utility world on the node of the call: the box, the scroll position, the
       scroll range and the scroll-padding of each. A level is a scroller, or a box that clips the element and that no
       notch moves. A scroller is an element whose overflow on an axis is `auto`, `scroll` or `overlay` and whose
       content is larger than its box there, and the document. A box that no notch moves is an element whose overflow on
       an axis is `hidden` or `clip` and whose content is larger than its box there (a carousel), and the document on an
       axis where its overflow is `hidden` or `clip`; the client's call gives it the state that Playwright's own input
       gives it (a script scroll moves a box with `hidden`, and no scroll moves a box with `clip`). The scrollers above
       an element with `position: fixed` do not move it. The stage reads the viewport (`Page.getLayoutMetrics`), and it
       finds the visible part of each level: its box within the viewport and within each level around it.
    2. When the element is in view, the stage answers `{}` with no scroll. An element is in view when on each axis all
       of it (with its scroll-margin) is inside the visible part of its nearest level (the viewport for an element with
       no inner level) less that level's scroll-padding, or its middle is in the middle 60% (vertical) or 80%
       (horizontal) of that part.
    3. Else the stage plans, for each level from the innermost out, the move that brings the element's middle to the
       middle of that level's box less its scroll-padding, within its scroll range, with no move on an axis where the
       element is in view of that box already; for each level, the element is clipped to the level inside it, after that
       one's move. When a box that no notch moves must move, the stage sends the client's call as it is, at once, and
       counts it. The round is the outermost scroller that must move, so that the scrollers inside it come into view
       first. The stage finds a wheel point over the visible part of that scroller (below). It moves the pointer there
       with a path when it is not there, and it sends the notches of that move: on each axis whose move is 1 px or more,
       `round(|move| / 120)` notches, and at least one.
    4. It waits for the smooth scroll to end (350 ms, a first value), reads again, and repeats, at most
       `STAGE_SCROLL_ROUNDS = 4` rounds. When the element is in view, it answers `{}`.
    5. When the element is still not in view, when a round did not move its scroller, when the in-flight bound stopped
       the path to the wheel point, or when no scroller can move it, the stage sends the client's call as it is (a
       script scroll), and logs and counts it.

    When the plan ends during the rounds (dialogs, above), or the main frame navigates, the stage sends the client's
    call as it is, at once. While the stage holds a button (the scroll of `dragTo`'s drop target), it sends the client's
    call as it is, and counts it: a path with no button would end the drag (board ab-t30.12 decides the drag).
  - The wheel point. A point over the visible part of the scroller is a wheel point only when all of these are true (the
    stage's own read):
    1. The element under the point, and each ancestor of it up to the scroller, is not an `input`, `select`, `textarea`,
       contenteditable, `canvas`, `embed`, `object`, `video`, `audio` or `iframe`.
    2. No element of the scroller (it, or an element inside it) that has a wheel listener (`wheel`, `mousewheel`) that
       is not passive has a box that holds the point or meets its column (rule 4). The stage reads the listeners of the
       page's own scripts on the scroller with its whole subtree, on each open shadow root inside it, and on each
       element assigned to a slot inside it that the scroller's own tree does not hold (`DOMDebugger.getEventListeners`
       with no `pierce`, on each root resolved in the page's main world with `DOM.describeNode` and `DOM.resolveNode`),
       and the boxes of their elements (`DOM.getContentQuads`), in at most 1,000 ms in all. A closed shadow root, and
       the roots after the first 32, stay out of the read. The listeners of the window and of the document do not count.
    3. The element under the point scrolls the target scroller: no other scroller comes before it on that chain.
    4. The point's column holds no element of rule 1 and no other scroller with a range on the axis of the move. The
       column is the line from the point along the round's move (the vertical axis first), as the page's content is now,
       also inside open shadow roots and in the elements assigned to their slots: the content that the notches move
       under the point. The elements around the element and inside it (in the flat tree), and the elements with
       `position: fixed`, which do not move, do not count. The element itself counts when it is a `canvas`, an `embed`,
       an `object`, a `video`, an `audio` or a frame, or when it has the focus and is an element of rule 1 (a focused
       number input changes its value under the wheel); a frame around the element at a level above it, and a
       cross-origin frame's owner, are around it and do not count. Chromium gives each wheel event of CDP to the element
       under the point at its time (measured by board ab-t30.11 on Chromium 156: an inner scroller that came under the
       point got the later notches of one `mouse.wheel`).

    The stage tries the page's last point first, then the points of a 5 x 5 grid over the visible part of the scroller,
    at 14%, 32%, 50%, 68% and 86% of it across and down, the nearest to the page's last point first. When no point
    passes, the stage sends the client's call as it is. A point over a frame is a wheel point of a scroller in that frame
    only when, at each frame level above the scroller, the element at the point is the frame's element.
  - An element in a cross-origin frame: the frame's session sends the call. The stage reads the box and the frame's
    scrollers there and maps them to the top page (the frame mapping, below). It reads the top page's scrollers on the
    frame's owner in the relay's own isolated world (`DOM.resolveNode` with the owner's `backendNodeId`), and it sends
    the notches on the top page's session at a point over the frame where the top page's element is the frame's owner.
    For an element of a cross-origin frame inside another cross-origin frame, the stage sends the client's call as it
    is, and counts it.
  - A retry's script scroll (the retry scroll recognizer, below) passes in the first build, and the stage counts it.
  - The Mac (with the stage on). Until the Mac's wheel model exists (part B, board ab-t30.7, and the input design's build
    task 9), the stage sends `mouseWheel` and `DOM.scrollIntoViewIfNeeded` on the Mac as the client sent them, with the
    stage's timestamp.
- Files: `DOM.setFileInputFiles` with `files` (Playwright's `setInputFiles` with paths and a local browser). The stage

- The recognizers. A utility call is a `Runtime.callFunctionOn` of Playwright's utility script,
  `(utilityScript, ...args) => utilityScript.evaluate(...args)`. Its arguments are, in this order: the utility script,
  two flags, the text of Playwright's function (the `value` of the fourth argument), the count of arguments, Playwright's
  serialized argument, and then the handles. In the serialized argument, a string, a number or a boolean is itself,
  `undefined` and `null` are `{"v": ...}`, a handle is `{"h": <index into the handles>}`, an array is `{"a": [...]}`, and
  an object is `{"o": [{"k": <key>, "v": <value>}]}`. A recognizer matches the whole text of the function with its
  pattern (a JavaScript regular expression), as `PLAYWRIGHT_FOCUS` does:

  | Recognizer | The pattern of the function's text | What the stage reads | What the stage does |
  | --- | --- | --- | --- |
  | hit-target check | `^\(\[injected\b[^\]]*\]\)\s*=>\s*injected\.setupHitTargetInterceptor\([^)]*\)\s*$` | `actionType`, `hitPoint`, the node, and the answer of the setup (a string is a miss of Playwright's first check) | for `hover`, the samples of the path outside the target before the setup; after a miss, the recovery |
  | the check's stop | `^\(([A-Za-z_$][\w$]*)\)\s*=>\s*\1\.stop\(\)\s*$`, with the handle that a hit-target setup of the tab returned as its first handle | its answer (`"done"`, or a miss at the first event) | after a miss, the recovery at the next setup |
  | focus | `PLAYWRIGHT_FOCUS`: `^\(\[injected\b[^\]]*\]\)\s*=>\s*injected\.focusNode\([^)]*\)\s*$` | the node | the focus click |
  | fill | `^async\s*\(\[injected\b[^\]]*\]\)\s*=>\s*\{[\s\S]*\breturn\s+injected\.fill\(node,\s*[\w$]+\);?\s*\}\s*$` | the node | the focus click |

- The hit-target check and its misses.
  - The miss watch. The stage reads the answer of each hit-target setup (a string is a miss of Playwright's first check)

**The scope's session (the peer check; board ab-v16.50).** Without the peer check the scope is
advisory: any process of the daemon's OS user can connect with any scope and get that scope's
list. With it, the relay admits a connection of a scope only when the process that connected
belongs to the agentwatch session of that scope. The relay reads that process from the kernel at
the accept, and walks from it through its parents to the session's root. No key, no token file and
no environment variable take part, so nothing that a transcript can leak gives access. The design:
agent-browser `docs/superpowers/specs/2026-11-05-peer-admission-design.md` (board ab-v16.47;
sections 3 to 6 and 9 to 11, measured on taylor; nothing ran on the Mac). The operator asked for it
in ab-dm6 ("see if we can solve it without adding a whole new key system") and kept the pane's
cgroup in ab-6gs.

- Words.
  - The **peer** of a connection is the process that called `connect()` on the client's side.
  - A **root** is a pair `(pid, start)`: the pid of a session's tmux pane process and the start time
    of that process. On Linux `start` is field 22 of `/proc/<pid>/stat` (clock ticks after the
    boot); on the Mac it is `pbi_start_tvsec * 1000000 + pbi_start_tvusec` of `proc_pidinfo`'s
    `PROC_PIDTBSDINFO`. A process **matches** a root when its pid and its start time are both the
    root's. A pid alone never matches: a pid comes back after its process ends (on taylor the pid
    space wraps in about 5.5 hours at 210 new pids per second; on the Mac `PID_MAX` is 99999).
  - The **walk** goes from the peer to its parent (field 4 of `/proc/<pid>/stat`; `pbi_ppid` on the
    Mac), and on.
  - The **pane's scope** (Linux) is the systemd scope `tmux-spawn-<uuid>.scope` that tmux makes for
    each new pane when its server can reach the user's D-Bus. A process's cgroup is the `0::` line
    of `/proc/<pid>/cgroup`. A cgroup is inherited at a fork and stays at a re-parent, so a job that
    left the tool's shell (`nohup ... &`, `setsid -f`, a double fork) stays in the pane's scope.
- Where the relay learns that the check is on: from its start, `agent-browser relay --socket <path>
  --peer-check`, not from an `allowlist` line (the relay drops the line at each link change).
- The self-test. With `--peer-check` only, at its start and before its endpoint socket listens, the
  relay tests its peer reader:
  1. It loads the reader: a dynamic `import("node:ffi")`, never a static import (on a Node without
     `node:ffi` a static import makes every agent-browser command fail at load with
     `ERR_UNKNOWN_BUILTIN_MODULE`: measured), then `dlopen` of libc (and of libproc on the Mac) and
     its symbols. A relay without `--peer-check` never loads `node:ffi`, so no other agent-browser
     command prints its `ExperimentalWarning` or depends on it.
  2. It makes a folder of mode 0700 with `mkdtemp` next to the endpoint socket, so that no other
     program can take part, and listens on a socket in that folder. The socket's path is at most 103
     bytes, as the endpoint's; a longer path fails the test.
  3. It starts a child process (`process.execPath` with a few lines of script) that connects to that
     socket and stays until the relay has read the connection.
  4. It reads the peer of the accepted socket and compares it with the child's facts: the pid (the
     child's pid), the uid (the relay's), the peer's parent (the relay's own pid) and the peer's start time
     (field 22 of `/proc/<pid>/stat`, or `proc_pidinfo` on the Mac: the relay must be able to read it), and, when
     `SO_PEERPIDFD` gives a pidfd, the pid that the pidfd names (the `Pid:` line of
     `/proc/self/fdinfo/<pidfd>`) and a `poll` of that pidfd, which must return 0 (the child lives;
     review-19 note 5). A connection from the relay to itself would not do: a reader of the wrong fd
     (the listening socket's) gives the relay's own pid too (measured).
  5. On Linux the answer of `SO_PEERPIDFD` selects the form of every later read: a pidfd of the
     child selects the **pidfd form**; `ENOPROTOOPT` (a kernel before 6.5) selects the **stat
     form**, which is not a failure; any other error fails the test. The Mac has one form.

  The whole test has a time limit, `SELF_TEST_MS = 5000`. In every path (a pass, a failure, the
  time limit) the relay stops the child and removes the folder (review-54b note 3). The relay logs
  the result on its standard error, for `agentwatch browser status` and the Browser page:
  `relay: the peer check runs (<form>)`, with `<form>` one of `pidfd`, `stat` and `mac`, or
  `relay: the peer check cannot run: <reason>`. When the import, the `dlopen`, a symbol, the listen,
  the child, the read, a compare or the time limit fails, the relay admits no connection, and it
  answers each upgrade with the 503 `the relay cannot read the program of a connection` (step 3)
  until it stops: it fails closed. The design's W2 (the relay asks the daemon over Node's IPC
  channel) is a later build, only if this test fails on a box that agentwatch runs.
- The peer read, at each accept, before the relay reads the request (step 3):
  - Linux: `getsockopt(SOL_SOCKET, SO_PEERCRED)` on the accepted socket gives the peer's pid and
    uid. In the pidfd form `getsockopt(SOL_SOCKET, SO_PEERPIDFD)` gives a pidfd of the same process.
    In the stat form the relay reads the peer's start time (field 22) at the accept too, so that the
    window of a reused pid starts there (review-54b note 4). The kernel records the peer at
    `connect()`: it stays that process after a fork, an exec, and a socket passed on with
    `SCM_RIGHTS` (measured).
  - The Mac: `getsockopt(SOL_LOCAL, LOCAL_PEERPID)` gives a pid, `LOCAL_PEERCRED` the uid, and
    `proc_pidinfo` the peer's start time, read at the accept. From the xnu source (not measured;
    board ab-v16.52) `LOCAL_PEERPID` is the last process that used the client's socket: at the
    accept, before the client sent its request, that is the connecter.
  - The peer's 403 (step 3) is the one answer for every read that fails at the accept (review-54b
    note 1): a `getsockopt` that fails, no pid (0), a uid other than the relay's, and in the stat
    form and on the Mac a start time that the relay cannot read. In the pidfd form any error of
    `SO_PEERPIDFD` is the peer's 403, whatever its code: a peer that exited and was reaped gives
    `EINVAL` on Linux 6.12, and the relay does not rely on the code.
- The session check (step 6), for a connection of scope S, in this order:
  1. The peer is alive. Pidfd form: libc `poll` of the pidfd (`POLLIN`, a 0 ms timeout) returns 0
     (not readable; 1, readable, means that the peer has exited, and -1, an error, counts as not
     alive too), the `Pid:` line of its `fdinfo` is the peer's pid (`-1` means that it was reaped),
     and the peer's `/proc/<pid>/stat` can be read and its state (field 3) is not `Z`.
     Each of the three counts alone: a process can show the state `Z` before its pidfd polls
     readable (a Node peer whose other threads still run), and a pidfd can poll readable while the
     state still shows `R` (both measured, review-54b note 2). Stat form and the Mac: the pid is
     still there, its start time is the one of the accept, and its state is not `Z` (on the Mac
     `pbi_status` is not `SZOMB`).
  2. The walk, from the peer itself (hop 0) to its parent, and on. It stops at the first process
     that matches a root of the line, of any scope (also a root that does not count, below);
     at pid 1; at a pid that has gone, or whose parent is 0; at a parent whose start time is later
     than its child's (the parent's pid came back during the walk, so it is not the child's parent;
     the same start time is a fork in the same clock tick, and the walk goes on; review-19 note 7);
     or after 32 hops (a root at most 32 parents above the peer counts). When it stops at a root of
     S that counts, the relay admits the connection. When it stops at any other root, the relay
     refuses it, whatever the cgroup says: so a process whose own walk reaches its own session's
     root never counts as another session, also when it joined another session's cgroup.
  3. On Linux only, and only when the walk stopped at no root: the peer's cgroup. The relay admits
     the connection when the peer's cgroup is the cgroup of a root of S whose cgroup counts, or a
     cgroup under it (`<root cgroup>/...`: a path under it, not a longer name with the same
     start). The Mac has no cgroups: the walk alone decides there.
  4. Before it admits, the relay checks item 1 again, so the `/proc` files that it read were the
     peer's. In the pidfd form it then closes the pidfd with libc `close`, as in every other path.

  Any check that fails gives the session's 403.
- The roots in the line (C10): `"roots":{"<scope>":[{"pid":<pane pid>,"start":<pane start>}]}`. A
  list, so that a session with more than one pane can name each; a root that one scope names twice
  is one root. The receiver never sees the roots. The line's rules:
  - A `roots` that is not an object applies as an empty object.
  - An entry whose scope does not match the scope pattern, or whose value is not a list, applies as
    absent.
  - An item that is not an object with an integer `pid` from 2 to 2^53 - 1 and an integer `start`
    from 0 to 2^53 - 1 is dropped, and the other items of its list apply. (2^53 - 1 is the largest
    integer that JavaScript holds exactly, so the relay and the daemon read the same number.) The
    other fields of an item are ignored.
  - A scope with no root that applies admits no connection (step 6). A root of a scope that
    `scopes` does not name still counts for the defensive root rules.
  - A relay with `--peer-check` that gets a line with no `roots` field applies the lists, and no
    scope has a root: step 6 refuses each connection.
  - A relay started without `--peer-check` that gets a line with a `roots` field (any value)
    applies no list of that line, as if no line had come: it closes the open connections (1008, no
    list any more) and answers each upgrade with the 503 `the allowlist has session roots, but the
    relay was started without --peer-check`, until a line without `roots` comes. So a daemon and a
    relay that disagree fail closed, with a clear text. The shared vector: `lines` in
    `test/vectors/scopes.json`.
- The defensive root rules. At each line the relay reads the `stat` and the cgroup of every root
  that applies, and from them it decides which roots count, so that the usual mistakes of a line (a
  pid of the tmux server, a pane that two scopes name, a pane with no scope of its own) admit no
  wrong session. They cannot catch every wrong line: a line that names another session's pane as a
  scope's root admits that session's processes to the scope, so the daemon must send each
  session's own pane (review-19 note 3):
  - A root counts only while it lives: the process with its pid has its start time.
  - A `(pid, start)` that two scopes name counts for neither scope.
  - A root that is an ancestor of another root (the walk from the other root reaches it, with the
    walk's own stop rules from its first hop: a parent whose start time is later than the other
    root's start time is no parent, so it is no ancestor; review-19b note 7) does not
    count, for the walk or the cgroup: a pane is never under another pane, so such a root is a
    wrong pid (for example the tmux server's).
  - A root's cgroup counts only when its pane has a scope of its own: the cgroup is not the cgroup
    of the root's parent (the tmux server's; on a box where tmux cannot reach D-Bus every pane stays
    there; a parent that the relay cannot read counts as the same cgroup), no live root of another
    scope has the same cgroup, and no other live root's cgroup is under it (a nested scope). A root
    whose cgroup does not count still counts for the walk.

  At a check the relay reads again only the scope's own roots (one `stat` and one cgroup read
  each): a root counts only while its start time matches, and its cgroup only while it is the
  cgroup of the line's read.
- The roots' life (the daemon; the daemon lead's part 3, the design's section 10):
  - The daemon sends the roots of every live session in each `allowlist` line, from the session's
    first line on: its pane's pid (`tmux list-panes -F '#{pane_pid}'`) and that process's start
    time.
  - At a launch, the daemon reads the new pane's pid and start (after `tmux new-session`, before the
    launch line) and does the pane's scope wait (below) before the scope enters its map, so the
    first line that names the scope carries its root, with the root's own scope cgroup. Else, in the
    moment between, a just-launched session would get the session's 403 (step 6) in place of the
    no-list 503 (step 5) that tells it to connect again. For such a window the session's 403 ends
    with `If this session started or restarted just now, connect again in a few seconds.`
  - The daemon starts the pane's shell first, and types the agent's launch line into it only after
    the pane is in its own scope. tmux moves a new pane's process into the pane's scope after its
    fork, and a process that the pane forks before that move stays in the tmux server's cgroup for
    its life (measured: the `tmux new-window` case of the design's section 4; review-54b note 6).
    On Linux the daemon reads `/proc/<pane pid>/cgroup` until it names a `tmux-spawn-<uuid>.scope`
    that is not the tmux server's cgroup, with a time limit (agentwatch picks it; a few seconds).
    It does not wait on the Mac (no cgroups), nor on a box where the tmux server cannot reach the
    user's D-Bus (`DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`): tmux makes no scope there, and the
    Browser page says that the pane's cgroup does not count on that box (review-54b note 5). When
    the time limit passes, the daemon types the launch line, and the Browser page names the
    session: its root counts for the walk only. agentwatch's launch does this today
    (`new-session -d` with the default shell, then the launch line), so this is a rule to keep.
    The daemon does this wait before it sends the first line that carries a new root, at a launch
    and at a respawn, or it sends that line again after the wait (review-19 note 1): tmux 3.5a moves
    the pane's process into its scope after the fork, and the relay reads a root's cgroup at each
    line, so a line from before the move gives the root its parent's cgroup (the tmux server's), and
    the root's cgroup does not count until the next line.
  - When a root changes (a respawned pane: a restart, an account swap, a resume), the daemon writes
    a line with the new root as soon as the new pane is in its own scope (the scope wait above),
    with the last confirmed object, before the agent starts in the new pane, and it does not wait
    for a `set_scopes` round trip: the receiver does not use the roots. Such a line comes only after
    the first `ok` on the current connection (review-19 note 6): the relay drops its line at each
    link change, and a line carries only an object that the receiver confirmed on the current
    connection (C10). Before that `ok`, the new root goes into the line that follows it. The daemon
    does not hold a respawn for that `ok` (review-19b note 3): in that window the agent can start
    in the new pane first and connect. The relay has no line yet (it dropped it at the link
    change), so the agent gets the 503 of step 4 (`its extension has not confirmed the allowlist`)
    and connects again. It gets no session's 403 for it.
    `tmux respawn-pane -k` gives the pane a new process and a new scope, so the old pane's jobs (in
    the old scope, under no live root) are refused, also by their cgroup, and the relay closes the
    connections of the old root (1008, when a connection ends).
  - At a session's end the daemon drops the scope's roots in the line that drops the scope (with
    5 b: that names it `null`; C4). Already before that line the pane has ended, so its root matches
    no process and its cgroup counts for no connection. A process of the ended session that still
    runs (a `nohup` job, a double-forked job, a command through a server that the session left
    running, such as a nested tmux server) then connects to no scope: for its own scope it gets the
    session's 403 until that line, and after it the no-list 503 (step 5) with 5 a. With 5 b it gets
    the session's 403 only until the line of C4's rule 3 drops the `null` entry: the line that ends
    the session names the scope `null` and gives it no root, so step 6 comes before step 7
    (review-19 note 2), and after the rule 3 line the scope is unnamed and step 5 gives the no-list
    503 (review-19b note 5); for any other scope it gets the session's 403. Its open connections closed at
    the `end_scope` (1000) or close at that line (1008). A later session of the same name has
    another pane, so another root (the operator's ab-6gs answer).
  - A session that agentwatch only stops (its agent ends, its pane stays) keeps its pane and its
    root until agentwatch ends the session: its jobs can still connect until then.
  - Over a daemon restart the daemon reads the pane of each live session again and sends its roots
    in its next line. So a session that was live before the peer check came gets its root in the
    daemon's first line after the deploy, and its processes are under its pane.
- What a program that no agentwatch session started gets: the session's 403 (step 6). A program in
  a plain terminal or an editor's terminal, the operator's own shell outside an agentwatch pane, a
  cron job outside agentwatch, and a command of `systemd-run --user` cannot connect. A cron job of
  agentwatch is a session of its own, with its own pane and root.
- Jobs that leave the tool's shell. With the walk alone (the Mac; a Linux box whose panes have no
  scope of their own) `nohup <job> &` in a shell that exits, `setsid -f`, a double fork and
  `systemd-run` are refused: an agent starts a long job with Claude Code's `run_in_background`, or
  without leaving the shell. On Linux with the pane's scope (P2, the operator's ab-6gs answer) such
  a job is admitted while it stays in the pane's scope; only `systemd-run` and a new tmux pane are
  refused.
- The limit (the daemon lead's point 3; the design's section 11). The check stops mistakes, an agent that
  names another session's scope, and an injected instruction that only names a scope. It does not
  stop a hostile process of the same OS user. Measured on taylor, such a process can join another
  session's pane scope with one write to `cgroup.procs`, run a command through a server that
  another session left running (`tmux -L <server> run-shell`: by the server's cgroup it then counts
  as that session), write into another session's MCP through `/proc/<pid>/fd/0`, and type into
  another session's pane with `tmux send-keys`. A process of a session can also pass an admitted
  connection on, or connect for another program: the check binds a connection to the session whose
  process connected. The key had the same limit (`/proc/<pid>/environ`).
- The operator's answer age-4ks ("env: no", 2026-11-04) stands: agentwatch puts no endpoint URL
  into a session's environment, and only `agentwatch browser endpoint` and `agentwatch browser env`
  print it, on request. The URL holds no secret, so an agent can give it to its own Playwright MCP
  as a plain argument: the MCP is a child of the agent, under the pane, and the walk admits it
  (measured). `agentwatch browser <command>` stays: agent-browser runs as the CLI's child, under
  the pane.
- The shared vectors: `upgradeChecks` and `lineCloses` in `test/vectors/endpoint.json` (each case
  gives the peer and a fake process table, so both sides test with a fake peer reader), and `lines`
  in `test/vectors/scopes.json`.
- A launch never waits for the agent browser. The daemon adds the scope to its map before the launch
  and sends `set_scopes` when the link is up. With `default` `null`, an earlier connection gets the
  no-list 503 (step 5), and the agent connects again.

**The MCP path (from stage 1d; the operator's answer Q1 of board item ab-bi3, 2026-11-10).** The service serves
the standard Playwright MCP (the answer Q4) over Streamable HTTP on a loopback TCP port. Nothing serves it before
stage 1d, and no session gets it before stage 3. The operator confirmed HTTP and added connection tokens (board item
ab-6ng), one for each session (ab-0wv): the token design gives the rules.

- The MCP port is off by default. The service opens it only when systemd passes it the socket of
  `agent-browser-mcp.socket` (the sd_listen_fds protocol), or in its `--test` mode with `--test-mcp-port <port>`: 0 (a
  free port that the kernel picks) or a port from 1024 to 65535, on `127.0.0.1`. It has no default port. As
  sd_listen_fds does, the service sets `FD_CLOEXEC` on each passed fd as soon as `LISTEN_PID` and `LISTEN_FDS` are its
  own, before it reads the names, and it removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment
  in every path: also in `--test` mode, where it takes no passed fd, and when only `LISTEN_FDNAMES` is set. When the take
  fails, the service opens no MCP port, and `status` says `failed` (C12). The service opens the MCP port before its
  control door, so the MCP's state, and with it the hello's features, is fixed before the first hello (C12).
- The URL is `http://127.0.0.1:<port>/mcp/<scope>`. The service listens on `127.0.0.1` only, on one port for
  each OS user and box. It holds no `[::1]` port.
- No secret is in the URL. A session's own MCP configuration holds the session's connection token in the
  `Authorization` header (`Bearer abt1_...`), in a 0600 file under agentwatch's tokens folder, and each request
  carries it only there.
- The service reads a token only from the `Authorization` header, never from the URL: a token in the query gives the
  request no token (the first 401 of step 7), and a token in the path is no scope of the connection (step 6).
- The scope in the path is a label, and it gives no right: the walk decides the scope (the admission, below).
  A request whose path names another scope than the walk's gets the session's 403. A request to `/mcp` alone
  names no scope, and the walk's scope applies.
- A local session reaches the MCP only through this URL. No stdio shim runs for it.
- On the endpoint's Unix socket the MCP path serves no local session: a request for `/mcp` there gets the 404
  of step 2, as today.
- The port stays held while the service is down, so another OS user cannot listen on it, and no connection
  ever starts `agent-browser.service`. On Linux a systemd user socket unit holds the port, and the service
  takes its socket from that unit; while the service is down, a connection waits with no answer (fail closed).
  The units are the daemon lead's proposal, which stage 1d proves (the self-contained design, section 19,
  build note 1).
- On the Mac the port refuses every connection (fail closed) until the Mac's TCP peer reader (`libproc`) is
  built and measured (stage 4). Until then a launchd holder accepts and closes each connection.

**The admission of the MCP path (from stage 1d; the daemon lead's conditions for the TCP choice).** At each new
TCP connection the service runs these checks in this order. The first check that fails gives its answer at
once, and the service then closes the connection. Steps 1 and 2 run before the service reads any byte of the
request.

1. The uid. The service finds the client's socket in `/proc/net/tcp` by the full tuple: the local address is
   the client's address and port, and the remote address is `127.0.0.1:<port>`. Exactly one line must match;
   no line or more than one gets the peer's 403. (A match by the client's port alone can match the service's
   own accepted socket.) The service reads the uid column of that line. A uid other than the service's gets the
   peer's 403 (`The agent browser cannot tell which program connects, so it refuses the connection.`), before
   any other check.
2. The walk. The service finds each process that holds the socket's inode (`/proc/<pid>/fd`), and walks each
   holder by the rules of the scope's session (above). Each holder must reach a root that counts, and all
   holders the roots of one scope: that scope is the connection's scope. No holder gets the peer's 403, which
   names no pid. A process whose `/proc/<pid>/fd` the service cannot read (a process of another user, or a process
   that is not dumpable) is no holder for this check: when no other process holds the socket, the connection gets the
   peer's 403. A holder that reaches no root, or holders of two scopes get the session's 403. So the walk
   refuses a browser process: Chrome is no session's process. Before the service's first `set_sessions` no root
   counts, so each connection with a holder gets the session's 403, whose text says to connect again in a few
   seconds (a refusal at step 1 and a connection with no holder still get the peer's 403). The
   service then reads the client's line of `/proc/net/tcp` again, and a line that
   changed gets the session's 403 too. The connection's scope gives its session, and `set_sessions` gives the
   session's `mcp_token` (from the one item of that scope: C12's rule of one scope once).
3. A request with an `Origin` header: its 403 (`A web page cannot connect to the agent browser.`).
4. A `Host` header that is not exactly `127.0.0.1:<port>` or `localhost:<port>`, no `Host` header, or two `Host` header lines or more (the service counts the header lines as the request carries them, as at step 7): 403 `The agent browser admits only the Host 127.0.0.1:<port> or localhost:<port>.`
   This check stops DNS rebinding. It keeps both forms, although each entry that agentwatch writes names
   `127.0.0.1`.
5. A path that is not `/mcp` or `/mcp/<scope>` with a scope that matches the scope pattern: 404 `Not found. Connect an MCP client to /mcp/<scope>.`
   The path is the request target as the client sent it, up to its first `?`, with no normalization: `/mcp/./<scope>`,
   `/mcp/x/../<scope>`, `//mcp/<scope>` and a percent-encoded scope get this 404. A query does not change the path.
6. A path whose scope is not the connection's scope: the session's 403.
7. The token (the token design). A request has an `Authorization: Bearer <token>` header when it has exactly one
   `Authorization` header line (the service counts the header lines as the request carries them, whatever the case of
   their name), and that header's value is `Bearer` (in any case), one space and a token of one character or more. The
   header's value is its field value without its leading and trailing spaces and tabs (RFC 9110), as Node's HTTP parser
   gives it: so `Bearer <token> ` with a space after the token carries that token, and `Bearer` with only spaces after
   it is not this form. The token is every character after that one space: after two spaces the token starts with a space, and
   text after the token is part of the token, so each is a token that the service does not know. A tab in place of
   the space is not this form. The service hashes the token with SHA-256 and compares the digest with the session's `mcp_token` in constant time. The first
   of these three cases that holds gives its answer:
   - no `Authorization: Bearer <token>` header: 401 `The agent browser needs this session's connection token. agentwatch adds it to the sessions that it starts while the repo's list has a site.`;
   - a session whose `mcp_token` is `null`: 401 `This session has no connection token. agentwatch adds one when it starts a session while the repo's list has a site: restart the session.`;
   - a token whose fingerprint is not the session's: 401 `The agent browser does not know this connection token for this session.`
     The text does not say whether the token belongs to another session.

   Each 401 carries `WWW-Authenticate: Bearer realm="agent-browser"`, with no `resource_metadata`, so no client
   starts an OAuth login (stage 2's live check proves it).
8. The readiness and the scope's list: the 503s of steps 4, 5 and 7 before the upgrade, with their texts. While this
   step would refuse with `its extension is not connected` or `its extension has not confirmed the allowlist` (Chrome is
   down, or its lists are not confirmed yet), a scope with no list, or a list with no site, gets the no-list 503 at once
   from the service's own snapshot (the start at a use, above); else the request passes this step with no start, and a
   request that needs no browser (`initialize`, `tools/list`, `ping`, a notification, a GET, a DELETE) goes on. Only a
   `tools/call` that the allow list takes then goes to the service's start at a use, as an upgrade does: it starts
   Chrome and waits, then steps 3 to 8 run again; a start that failed, or a check that still fails, gives its answer to
   that call. A tool call whose client leaves while it waits never reaches the MCP. On the
   MCP path a scope whose list has no site gets the no-list 503 too: the list is the allow (the token design, sections
   6.5 and 7.2). The endpoint keeps its own rule: there a scope whose list is empty is admitted, and it can open
   `about:blank` only. The self-test's 503 of step 3 before the upgrade does not apply here: this check reads `/proc/net/tcp`,
   `/proc/<pid>/fd` and the `stat` files, and needs no `node:ffi`. When the service cannot read
   `/proc/net/tcp`, each connection gets the peer's 403 at step 1.

- The pid of the session's 403 (`<pid>`): the lowest pid among the holders that the walk refused. When the walk
  refused no holder (holders of two scopes, a line that changed, or step 6), it is the lowest pid among all the
  holders. A connection with no holder gets the peer's 403 (step 2), so the session's 403 always names a holder.
- Steps 1 and 2 run once for each connection, and a connection keeps its scope until it closes. Steps 3 to 8
  run for each request on the connection. A refused request never has its header in a log line or in an answer.
- After the first refusal of steps 3 to 8 the connection closes, and a later request that the client sent on it (a
  pipelined request) gets no check, no answer and no handler. A request with `Expect: 100-continue` runs steps 3 to 8
  before the service sends `100 Continue`; a request with another expectation runs steps 3 to 8, then gets 417
  `Expectation Failed`, and the connection closes. A `CONNECT` request gets no answer, and the connection closes.
- An exception of the service while it checks or answers a request gives 500 `The agent browser could not answer this request.`,
  which echoes nothing; the connection closes, and the service goes on.
- The timeouts of an admitted connection (first values): a request's header comes whole within 10 s of the admission
  or of the end of the last answer on the connection, and a request's body pauses for at most 30 s; else the service
  closes the connection with no answer. While the service works on a request, no timeout runs.
- A request with the MCP session id of another scope, or with an MCP session id that the service does not
  know, gets the 404 of an unknown MCP session: the transport's answer to an unknown `Mcp-Session-Id` (the
  self-contained design, section 8.2, M3).
- An `Origin` header, a wrong `Host` and the walk's refusal of a browser process are three separate checks, and
  the service keeps all three.
- At C12's `session_ended`, the service closes the scope's MCP connections and ends its MCP sessions.
- At each C12 `set_sessions`, the service closes each MCP connection when a root that admitted it no longer counts
  for its scope, also when only that root's cgroup stops counting for a connection that the root's cgroup admitted,
  and each MCP connection of a session that the snapshot drops or whose `mcp_token` changed. This rule is the MCP
  path's own: the endpoint's 1008 close at an `allowlist` line (when a connection ends, above) asks only whether the
  line still names the root. It also ends the
  MCP sessions of each such session, as at `session_ended`: of a session that the snapshot drops or whose `mcp_token`
  changed (also when it has no open connection), and of a scope whose connection closed for its root.
- The shared vectors: `mcpChecks` and `mcpCloses` in `test/vectors/endpoint.json`, with `mcpSnapshots`,
  `mcpLists`, `mcpTokens`, `mcpSessionIds` and `mcpAnswers` (each case gives the lines of `/proc/net/tcp`, the holders and a
  fake process table, so both sides test with a fake reader; the tokens are made-up test values).

**The limits of the MCP path's admission (from stage 1d; the self-contained design, sections 8.3 and 18, M2).**

- The check finds the holders of the socket, not the process that connected. A process that forks after its
  connect has a child that holds the socket too, and that child must be in the same session.
- A client that writes its request and exits at once is refused: no process holds the socket at the check
  (M2: 50 of 50).
- The check costs 10.4 ms p50 to 23.1 ms p50 on taylor (M2), once for each connection.
- A client of another OS user is refused by the uid column; M2 reasoned this case and did not run it.
- As on the endpoint, the check does not stop a hostile process of the same OS user. The token does not change this: a
  process of the user can read every session's entry file. A token works only from its own session, and it ends with the
  session. The stored sign-ins do not change this: such a process can replace the service and wait for the operator's
  next unlock, or use the display's X authority during an act.
- The path rule of the MCP inside the service (below) does not stop a process of the same OS user either: it can put a
  link or a hard link to another file into the scope's folder, or change a file between the service's check and the
  MCP's open of it.

**The MCP inside the service (from stage 1d; the self-contained design, section 8.2).**

- The service makes one Playwright MCP server object for each MCP session, from the pinned `@playwright/mcp`
  package's public entry. At most 4 MCP sessions for each scope and 32 for each service (first values). One more
  `initialize` gets HTTP 503 with the JSON-RPC error `-32000` and the text `The agent browser serves at most 4 MCP sessions for each agentwatch session. End one of this session's MCP sessions (DELETE), then initialize again.`
  or, at the service's limit, `The agent browser serves at most 32 MCP sessions, and each is in use. Initialize again later.`
- Its configuration is fixed: the scope's CDP endpoint and the default context; the capabilities named
  explicitly, never `core-install`, `storage`, `devtools`, `testing` or `config`;
  `allowUnrestrictedFileAccess: false`; and an output folder for each scope in the state folder.
- Its configuration also sets `timeouts.action: 30000` in `createConnection`, in place of the MCP's default of 5 s, so
  that an action that the input stage (above) translates ends inside the MCP's action timeout.
- It also sets `webmcp: false` (a page's own tools: their listing runs page code, and no allow list names them) and
  `saveSession: false`. The scope's CDP endpoint comes through the context getter of `createConnection`, which connects
  with the ticket (below) and gives the default context: with `browser.cdpEndpoint` in the configuration the package
  would also start a pipe server for the browser in the temp folder and write a server registry entry, which another
  program of the user could use to reach the browser around the agent door. So the MCP never launches, downloads or
  binds a browser.
- The service answers the MCP server's `roots/list` itself, with the scope's folder, so the MCP's own file guardrail
  and its relative file names use that folder. It answers each other request of the server to the client with
  `Method not found`, and it drops the server's notifications (the transport sends no stream).
- Tools and argument keys pass only through the allow list (`docs/contracts/mcp-allow-list.md`), and the service's own
  tools of the allow list's `service_tools` only for a request that the MCP port admitted with the walk (a local
  admission: the sign-in act, below).
- The service refuses each argument that the allow list marks as a path when the path is outside the scope's
  folder, `<state>/mcp/<scope>/`, after `realpath`. A relative path is read from the scope's folder; for a file that
  does not exist yet the service takes the `realpath` of its deepest folder that exists. A value that is no string and
  no list of strings is refused as a path. The service makes `<state>/mcp` and the scope's folder, each with mode 0700,
  at the scope's first MCP session. At each path argument it reads both with `lstat`: when one of them is a link or no
  folder of the service's user, it refuses each path argument with the format's answer (a call with no path argument
  passes).
- The scope's folder lives as long as the scope's agentwatch session (review-115 note 3). At C12's `session_ended`, and
  at each C12 `set_sessions` for each scope that the snapshot names neither in `sessions` nor in `remote` (also a session
  that ended while the service was down, which got no `session_ended`), the service ends the scope's MCP sessions and,
  after the request's answer and once every worker of the scope has stopped, removes the scope's folder with its files.
  So a later session of the same launch name does not read the files of an earlier one, and its first MCP session makes
  the folder again; an MCP session of the scope that begins before those workers have stopped keeps the folder and its
  files. While two live sessions share a launch name, the daemon sends no item for that name (C12, the field rules; the
  vectors' `r14`), so the service removes that name's folder while the earlier session lives, as it removes the list
  copy (C12). The service removes only a folder or a link whose name is a scope, and only while `<state>/mcp` is a
  folder of the service's user that is no link; a link in the scope's place or in the folder goes as a link, and its
  target stays, and another entry of a scope's name (a plain file) stays. A removal that fails gets a log line with the
  scope and the error's code, never a path. The service's own stop removes no folder.
- The MCP's Playwright connects back to the endpoint's CDP path with the MCP session's scope and a one-time
  ticket, which only a connection from the service's own pid can use. Every rule of this file applies to that
  connection.
- The ticket is 32 random bytes in base64url, in the query of the CDP path: `/devtools/browser/<scope>?ticket=<ticket>`.
  The service makes a new ticket for the worker at each connect of the MCP's browser: at the first tool that needs the
  browser, and again at the next such tool after `browser_close` or after the endpoint closed the connection (a 1008
  close, for example). A ticket lives 30 s (first value), and
  it is gone after its first check, whatever the result. In the agent door's checks before the upgrade, the ticket
  takes the place of the walk at step 6: a connection from the service's own pid passes it only with a live ticket of
  its scope, and no root admits it; with no such ticket it gets the session's 403. A ticket from any other pid admits
  nothing, and that connection gets the walk. The ticket never leaves the service's process, and no log line holds
  it.
- The MCP code of each scope runs in one worker thread of the service, with a heap limit (first value
  512 MiB). A worker that passes it ends with its MCP sessions, and their clients get an error.
- The service starts a scope's worker at the scope's first MCP session and stops it with its last. The worker has an
  environment of its own (no variable of the service's environment reaches it), and the service reads and drops its
  standard output and error. When a worker passes its limit, each request that waits for it gets the JSON-RPC error
  `-32603` with the text `This MCP session has ended: the MCP of its agentwatch session passed its memory limit. Initialize a new MCP session.`
  (after a failure of the worker: `This MCP session has ended: the MCP of its agentwatch session failed. Initialize a new MCP session.`;
  an `initialize` whose server object is not made yet gets the 503 of the transport's table), and each later request of
  those MCP sessions gets the 404 of an unknown MCP session. The model, Chrome, the doors and
  the other scopes' workers go on.
- No log line of the MCP path holds a tool argument, page content, a cookie, a URL path, a payload, a username, a
  password, a form value, an `Authorization` header, a token, a token's fingerprint or a lifetime id, and a request that
  the service refuses for its size or its shape is never logged (the log rule of C12).

**The transport of the MCP path (from stage 1d; the self-contained design, section 8.2).** The service's own small
Streamable HTTP transport, with no MCP SDK package, answers each request that passed steps 1 to 8, with JSON only:

- A `POST` carries one JSON-RPC message, and a request gets one answer with `Content-Type: application/json`. A batch
  gets HTTP 400 with `-32600` and `Invalid Request: the agent browser takes one JSON-RPC message in each POST.`; a body
  that is no JSON gets HTTP 400 with `-32700` and `Parse error`; a body of more than 1 MiB (first value) gets HTTP 413
  with `-32600` and `Request too large: the agent browser takes at most 1048576 bytes in one POST.`, and the
  connection closes.
- `initialize` makes a new MCP session: its id, 32 lowercase hex digits, is in the answer's `Mcp-Session-Id` header.
  An `initialize` with an `Mcp-Session-Id` gets HTTP 400. Each other message carries the session's id: with none it
  gets HTTP 400 with `-32000` and `Bad Request: this request needs the Mcp-Session-Id of its MCP session; initialize first.`;
  an unknown id, or an id of another scope, gets the 404 of an unknown MCP session: HTTP 404 with `-32001` and
  `Session not found`.
- Of the requests only `initialize`, `ping`, `tools/list` and `tools/call` reach the MCP; each other request gets
  `-32601` and `Method not found`. Of the notifications only `notifications/initialized` and
  `notifications/cancelled` reach it, and the others are dropped. A notification or a client's answer gets HTTP 202
  with no body. A client that closes its connection before its answer cancels that request: when the MCP has the
  request, the service sends it `notifications/cancelled`, and the service frees the request's id at once (the MCP
  never answers a request that it cancelled), so a later request with that id goes on. A client's own
  `notifications/cancelled` of a request of its MCP session that still waits reaches the MCP too, and it frees that id at
  once; the request's POST, while it is open, gets HTTP 200 with `-32800` and `Request cancelled: the client sent notifications/cancelled for this request.`
  (a tool call that waits for the start at a use gets it when that wait ends, or that wait's refusal). The MCP has no
  code of its own for a cancelled request, and `-32800` is the code that the Language Server Protocol gives one. The
  pinned MCP ignores a cancel whose `requestId` is `0` or `""`, or whose `params` its schema refuses (a `reason` that is
  no string), and it then runs the call and answers it. So once the MCP has the request, such a cancel frees nothing:
  the id stays busy and a tool call counts as a use until the MCP's answer, which goes to the POST while it is open;
  for a client that closes its connection, the service sends no cancel for the id `0` or `""`.
- A `GET` gets HTTP 405 with `Allow: POST, DELETE`: the service sends no stream. A `DELETE` with the session's id ends
  that MCP session: HTTP 200 with no body.
- At `session_ended` and at the close at a change, each request of an MCP session that ends while it waits gets
  `-32603` and `This MCP session has ended: its agentwatch session ended or changed. Initialize a new MCP session.`
  (an `initialize` whose server object is not made yet gets the 503 of the table below).
- No log line of the transport holds an MCP session id; a line names an MCP session by its number.

The transport's answers: each answer of an error carries the request's id, or `null` when the request has none that
the service can read (a body that is no JSON-RPC 2.0 message of the shapes below has none). The transport gives no other answer than these, the HTTP 200 answers of the allow list's format
(`docs/contracts/mcp-allow-list.md`), the 202 and the 200 above, and the MCP's own answers: the result or the JSON-RPC
error that the MCP gives to a request that reaches it, which the transport passes on with HTTP 200 (for `tools/list`,
with only the list's tools and keys).

| Case | HTTP status | JSON-RPC code | Text |
| --- | --- | --- | --- |
| A batch | 400 | `-32600` | `Invalid Request: the agent browser takes one JSON-RPC message in each POST.` |
| A body that is no JSON | 400 | `-32700` | `Parse error` |
| A body that is JSON but no JSON-RPC 2.0 message of the three shapes below, also a message whose id is no string and no safe integer | 400 | `-32600` | `Invalid Request` |
| A request whose id is the id of a request of the same MCP session that still waits | 400 | `-32600` | `Invalid Request: a request with this id still waits in this MCP session.` |
| A body of more than 1 MiB | 413 | `-32600` | `Request too large: the agent browser takes at most 1048576 bytes in one POST.` |
| An `initialize` with an `Mcp-Session-Id` | 400 | `-32600` | `Bad Request: initialize makes a new MCP session, so it carries no Mcp-Session-Id.` |
| Another message with no `Mcp-Session-Id` | 400 | `-32000` | `Bad Request: this request needs the Mcp-Session-Id of its MCP session; initialize first.` |
| An `Mcp-Session-Id` that the service does not know, or one of another scope | 404 | `-32001` | `Session not found` |
| A `GET`, or a method other than `POST` and `DELETE` | 405 | `-32000` | `Method not allowed: the agent browser's MCP sends no stream; POST each message, and DELETE ends the MCP session.` |

| A request of an MCP session that ends while it waits (`session_ended`, the close at a change, a `DELETE`) | 200 | `-32603` | `This MCP session has ended: its agentwatch session ended or changed. Initialize a new MCP session.` |

- The service cannot make an MCP session when the scope's worker does not make the session's server object within
  30 s (first value) or fails to make it, when the session ends before its server object is made (`session_ended`, the
  close at a change, the worker's heap limit or failure), or when the service stops. An `initialize` whose MCP session
  ends after its server object is made gets the `-32603` answer of its end, as any request that waits.
- A JSON-RPC 2.0 message is a JSON object with `jsonrpc` `"2.0"` in one of three shapes, with no other member: a
  request (`jsonrpc`, an `id`, a `method` that is a string, and a `params` or none), a notification (`jsonrpc`, a
  `method` that is a string, and a `params` or none), or a client's answer (`jsonrpc`, an `id`, and exactly one of
  `result` and `error`). A `params` is a JSON object; its `_meta`, when it has one, is a JSON object whose
  `progressToken`, when it has one, is a string or a safe integer, and whose `io.modelcontextprotocol/related-task`,
  when it has one, is a JSON object with a string `taskId`. An `id` is a string or a safe integer: an integer from
  -(2^53 - 1) to 2^53 - 1 (a larger one loses its exact value in the service's JSON parse). The shapes of a request and
  of a notification are exactly the shapes that the MCP's own SDK takes: it gives no answer to a request of another
  shape (the pinned version: an extra member, a `params` that is no object, a `_meta` that is no object), so a body of
  another shape never reaches the MCP. A client's answer never reaches the MCP (the service sends no request to the
  client), so its shape is the transport's own (the SDK would also take an error with no id). A
  request whose id is the id of a request of the same MCP session that still waits never
  reaches the MCP either, and the waiting request keeps its own answer. A request waits until its answer or its cancel,
  from the moment that it passes the transport's checks (a tool call also while it waits for the start at a use).

**How a session gets the MCP (from stage 2; the operator's answer Q2 of ab-bi3, and the daemon lead's condition 4).**

- agentwatch writes the MCP's HTTP entry into a session's own MCP configuration at the session's launch, only
  when the session's scope has a list with at least one site. agentwatch mints the session's token at the launch,
  sends its fingerprint in `set_sessions`, writes the entry file before the launch and removes it at the session's
  end.
- Each entry that agentwatch writes names `127.0.0.1`, never `localhost`: the service listens only on
  `127.0.0.1`.
- agentwatch writes the entry only when the `LISTEN` line of `127.0.0.1:<port>` in `/proc/net/tcp` has the
  user's uid. Otherwise it writes no entry, and `agentwatch health` shows red.
- agentwatch never writes the entry into the user's global files. For Claude Code it writes a file for the
  session under its tokens folder (`tokens/agent-browser/sessions/<random name>.json`, 0600, with a new random name
  for each run), which the launch passes with `--mcp-config`. For Codex it writes the session's profile file under
  its tokens folder and a link to it in the session's Codex home (`aw-<random name>.config.toml`), and the launch
  passes `-p aw-<random name>`; a Codex session with agentwatch's app server gets no entry until a Codex release
  lets the app server read a profile (the token design's answer E a). No command line holds a lifetime id.
- Nothing goes into the session's environment: the operator's answer age-4ks ("env: no") stays.
- agentwatch does not change a running session's MCP configuration. A list that gets its first site after a
  session's launch takes effect at that session's next launch, so the session needs a restart.

**The merge guard (board ab-v16.99; the operator's rule of 2026-11-12).** The design is
`docs/superpowers/specs/2026-11-13-triage-merge-guard-design.md`. The operator's rule (agentwatch board item age-zbo): "No
PR from automatic issue triage is allowed to be merged, even if i've already given agents authorization to merge to
staging." The model refuses an agent's merge of a triage PR (each method), its Ready for review, its auto-merge and its
approve, the same actions as agentwatch's own merge hook, for every scope and every client: the agent door, the MCP
inside the service, and the relay of the old path. The receiver's floor (C10's `bridge.mergeGuard`, C5's merge guard's
floor) adds the tabs that no client holds. agentwatch's hook covers `gh` and the API from a shell; this guard covers the
browser path: an agent's input, and the page's own requests.

- The marker: one definition, the same as agentwatch's merge hook (the manager's decision, which the daemon lead and the
  operator's rule share). A PR is marked when any one holds: one of its labels equals `agentwatch-triage` or `triage`,
  compared without case (GitHub compares label names without case); its title starts with `[agentwatch triage]` or
  `[triage]`, compared without case, with no trailing space needed; its head branch starts with `agentwatch-triage/` (an
  extra sign). The bare forms `triage` and `[triage]` are there because hand-started triage PRs carry them; agentwatch's
  built feature uses `agentwatch-triage` and `[agentwatch triage]`. A false match only refuses a merge, the safe side of
  the operator's rule.
- The hosts. The guarded hosts are GitHub's: `github.com` and each of its subdomains (`api.github.com` among them). Only
  the service's `--test` adds one more, with `--test-merge-guard-host <host>`: a normalized host under `.localhost`, a
  stand-in of GitHub for the live check. The service refuses that flag without `--test`, and a host that is not under
  `.localhost`. A write is a request to a guarded host whose method is not `GET`, `HEAD` or `OPTIONS`.
- The verdicts. The model reads GitHub's own answers of a PR's URLs at Fetch's response stage, with
  `Fetch.getResponseBody`: `/<owner>/<repo>/pull/<n>` and its sub-paths, `/<owner>/<repo>/issues/<n>`, and on the API host
  `api.<host>` `/repos/<owner>/<repo>/pulls/<n>` and `/repos/<owner>/<repo>/issues/<n>`. A 2xx answer that shows a form
  of the marker makes the PR marked: a label as its link (`/labels/<name>`), its `data-name`, its JSON `"name"` or a
  search's `label:<name>`; a title prefix at the start of the page's `<title>`, of an element's text, of a `title`
  attribute or of a JSON `"title"`; the head branch's prefix anywhere (each also with its characters escaped). Only the
  PR's own page (the conversation, `files`, `commits` or `checks`) as a 2xx HTML answer that names the PR's path, or the
  PR's API object (`/repos/<owner>/<repo>/pulls/<n>`) as a 2xx JSON answer with its number, with no form of the marker,
  makes it unmarked. A PR that the model saw marked stays marked for the model's life. Every other PR is unknown. The
  verdicts hold for every scope; a PR of the stand-in host is never a PR of GitHub. The model also keeps the node ids
  (`PR_...`) of each marked PR's answers.
- The judge. The model refuses a write, in this order: when the tab's page (its last top URL, from `tabs.onUpdated` or
  the top frame's document request) or the request's `Referer` is a PR page that is marked or unknown (so no write
  leaves a triage PR's page: no merge, Ready for review, auto-merge, approve, comment, or edit of its label or title);
  when the request names a marked PR, or its URL or body names a node id of a marked PR; when it is a merge of branches or
  a write of a ref (`/repos/<owner>/<repo>/merges`, `/repos/<owner>/<repo>/git/...`, `git-receive-pack`, or a GraphQL
  `mergeBranch`, `updateRef` or `updateRefs`); when it is a merge-type action of a PR (a path segment after `/pull/<n>/`,
  or after the API's `/pulls/<n>/`, that holds `merge`, `ready`, `queue` or `review`) that is not known unmarked, or a
  merge on no PR (a path segment that holds `merge` or `enqueue`) from a page that is no known-unmarked PR; when it is a
  GraphQL request (the last path segment holds `graphql`) whose body Chrome did not give or that is larger than 1 MiB;
  and when it is a GraphQL request whose body names `mergePullRequest`, `enablePullRequestAutoMerge`,
  `enqueuePullRequest`, `markPullRequestReadyForReview`, `addPullRequestReview`, `submitPullRequestReview`,
  `mergeMethod` or `APPROVE`, from a page that is no known-unmarked PR. Every other write goes.
- The side that it fails to. When the model cannot tell (a page of an unknown PR, a merge-type action of an unknown PR,
  a GraphQL body that it cannot read), it refuses: the rule allows no agent's merge of a triage PR, the browser cannot
  undo a merge, and a refused merge of another PR costs one step (load the PR's page, then try again).
- What the agent sees. The model answers a refused write itself with `Fetch.fulfillRequest`, so the request never
  reaches GitHub: HTTP 403 with `Cache-Control: no-store`; for a document (a form's POST) a `text/plain` page of the
  text; for any other request `{"message":"<text>","errors":[{"type":"FORBIDDEN","message":"<text>"}]}`, with
  `Access-Control-Allow-Origin` of the request's `Origin`. When that answer fails, the request fails with
  `BlockedByClient`. The texts:

  | Reason | The text |
  | --- | --- |
  | marked | `The agent browser refused this request: the pull request came from agentwatch issue triage. No agent merges such a pull request, marks it ready for review, turns on its auto-merge, approves it or changes it in the agent browser; only the operator does, on GitHub (the operator's rule, 2026-11-12).` |
  | unknown | `The agent browser refused this request: it could not tell whether the pull request came from agentwatch issue triage, and no agent merges such a pull request (the operator's rule, 2026-11-12). Load the pull request's own page in this tab, then try again.` |
  | untied | `The agent browser refused this request: it cannot tie the request to a pull request that did not come from agentwatch issue triage (a merge of branches, a write of a branch, or a GraphQL request that it cannot read), and no agent merges such a pull request (the operator's rule, 2026-11-12).` |

- The guard's Fetch. Before a client gets its first session of a tab, the model turns on its own `Fetch` in the tab with
  its patterns: each URL of a guarded host at the request stage, and the PR URLs and `api.<host>/repos/` at the response
  stage. It turns it on in each child session that Chrome attaches in that tab (a frame or a worker of the client's
  auto-attach) too, before the client lets the child run. A client's `Fetch.enable` there goes to Chrome with the guard's
  patterns and the client's; a client's `Fetch.disable` goes as a `Fetch.enable` of the guard's patterns, and the model
  lets each request that the client held go on (a refused write with its 403). The model judges and reads each paused
  request of a guarded host before any client gets it; a client gets it then only when its own patterns ask for it, so a
  client that intercepts (Playwright's `page.route`) still sees each request of a GitHub page. A pause that no pattern of
  the client asks for goes on (`Fetch.continueRequest`); a `Fetch.authRequired` of a guarded host gets `CancelAuth`, and
  another one that the client does not handle gets `Default`.
- The clients' Fetch commands. A Fetch command whose `requestId` names a request that the model holds (one of a guarded
  host, until it has judged or read it) gets `Invalid InterceptionId.` A client's `Fetch.continueRequest` of a refused
  write goes to Chrome as the model's `Fetch.fulfillRequest` with the 403 (a client's own `Fetch.fulfillRequest` or
  `Fetch.failRequest` of it goes as it is: neither reaches GitHub). A `Fetch.continueRequest` that changes the `url`,
  `method`, `postData` or `headers` of a request of a guarded host, or whose `url` is on a guarded host, gets `Not available in the agent browser: a request to <host> that a client changes (Fetch.continueRequest). The agent browser judges each request to GitHub itself (the merge guard of pull requests from agentwatch issue triage).`,
  and it does not reach Chrome: the model answers that request itself with a 403 of the same text (a client such as
  Playwright's `route.continue` drops a protocol error, so the request never waits for it). A redirect to a guarded host
  is a new request at the request stage, which the model judges.
- The page's policy. While the model has no floor that the receiver confirmed on the current link (no answer yet to
  `bridge.mergeGuard`, an `unknown op` answer, an error, or a link change before the answer), `Page.setBypassCSP` with
  `enabled` true gets `Not available in the agent browser: Page.setBypassCSP.` So with no floor a page's Content Security
  Policy stays in force, and a client starts no worker of its own script where the page's policy forbids it. With a
  confirmed floor it goes to Chrome as before. A page's request never goes through a service worker in a tab whose bypass
  is on (the page's service worker, below). A worker's own request (a shared worker's or a service worker's) has no tab,
  and the floor blocks each write of it. A dedicated worker's request goes through the tab's own session, also with no
  auto-attach of the client (measured: the live check of board ab-v16.99), so the model judges it; only a blob worker of a
  page that a service worker controls sends its requests through that service worker (the page's service worker, below).
- The page's service worker (the operator's answer of 2026-11-13 on board item ab-u92, "On GitHub only": "Other sites

**The sign-in act (from stage 1e; the stored sign-ins design, board ab-v16.95).** The design is
`docs/superpowers/specs/2026-11-10-stored-sign-in-credentials-design.md`, sections 4, 7 and 8, with the operator's
answers of 2026-11-10 (board item ab-8w8: Q1 a, Q2 b, Q3 b, Q4 a). The service's model builds the act in stage 1e part
2 (board ab-v16.97.4), off by default, and it serves sessions from stage 3. The store, its ops and the act's events are
C12's (the stored sign-ins). The relay has no sign-in act: it refuses both methods as calls outside its set
(`Not available in the agent browser: <method>.`). On the Mac the store and the act stay off until stage 4 measures
whether another program of the same user can read the service's memory.

- What the act does. An agent asks for a sign-in by the name of a credential that the operator stored. The service
  types the credential's username and password into a tab of its own that no client can reach, and moves the
  sign-in's cookies and `localStorage` into the default context. No answer, event, status or log line holds a
  username, a password or a form value.
- The entry.
  - CDP: `AgentBrowser.signIn` with `{"name":"<name>"}` and `AgentBrowser.signIns` with `{}`, on the root session or
    on a browser session of the agent door. The model answers both (where each call goes, above). On a page session
    the model refuses both with `Not available in the agent browser: <method>.`, and they never reach Chrome.
    Playwright sends them on a browser CDP session:
    `const s = await browser.newBrowserCDPSession(); await s.send("AgentBrowser.signIn", { name: "staging" })`.
  - The CLI: `agent-browser sign-in <name>` and `agent-browser sign-ins`, and `agentwatch browser sign-in <name>`, a
    thin wrapper. They send the method over the agent door, so the walk gives the scope.
  - The MCP: the service's own tools `browser_sign_in` (`name`) and `browser_sign_ins` (no argument), of the allow
    list's `service_tools`. The service runs them as the method for the MCP session's scope, only for a request that
    the MCP port admitted with the uid check and the walk (a local admission). A request that a remote token admitted
    (stage 5: the token design, section 10) gets a `tools/list` without them, and a call of either name gets the
    refusal of check 1.
  - `AgentBrowser.signIns` answers the store's state and the names and the origins that the caller's scope may use
    (checks 2 and 3, below): `{"state":"none"|"locked"|"open","signIns":[{"name":"<name>","origin":"<origin>"}]}`.
    Names and origins are not secrets. It refuses only by check 1, and it sends no `sign_in` event (C12).
- The checks before the act, in this order. The first check that fails gives its text (what the agent sees, below),
  and no act starts.
  1. The request came by a local admission: the agent door (the kernel's peer check and the walk), or the MCP port
     with the uid check and the walk. A request on the MCP's ticket connection to the endpoint has the admission of its
     MCP session. A request that a remote token admitted never reaches a later check. The agent browser is ready (the
     readiness, before the upgrade).
  2. The last `sign_ins` (C12) holds a record of that `name` whose `approved` is `true`, and the scope's list covers
     the record's host. With the answer Q2 b, each scope whose list covers the host may use the credential: a
     credential names no repos. No such name, a name whose host the scope's list does not cover, and an offer that
     waits get the same text. Two approved records of one name in the last `sign_ins` each break (C12, names and ids),
     so check 2 finds neither of them, and the request gets that text too (C12's vector `checkTwo`).
  3. The scope's list covers each host of the record's `send_to`.
  4. The store is open (C12).
  5. The record opens: its seal's tag holds with its plain fields as the additional data, so its `approved` is `true`
     in the seal too; its `gen` is not lower than the highest `gen` that the service saw for its `id`; and its `id`
     is not a removed id.
  6. The credential is not stopped, and fewer than 6 of its acts started in the last hour.
  7. No other act runs. An act waits for the act before it, at most 60 s. A request that waited is checked again at
     its turn: checks 4, 5 and 6 run again before the act starts, and the record's values open only then, so a stop of
     the credential or the hour's last act by an act before it, or a lock during the wait, refuses it as a check
     before the act does.
  - The act is a use for the start and the stop by use (board ab-v16.94.11): an act that finds Chrome down starts it,
    and Chrome does not stop while an act runs.
  - A request that a check refuses is no act: it counts for none of the hour's limit of 6, the acts of C12's `status`
    and the results in a row of the lockout guard (below). It sends one `end` event with an act id of its own and no
    `start` (C12, the stored sign-ins), within the rate of the refusal ends: at most 10 for one scope in any 60 s;
    past that, one a minute, which carries `dropped`, the number that did not go (C12). Each refused request still
    gets its answer and its log line.
- The act window and its context.
  - The receiver opens the act window with C10's `windows.create`, `incognito: true`, `focused: false` and the mark of
    an act (the receiver's part of the stored sign-ins, board ab-v16.97.3), with the caller's scope for the list rules
    (C4, C5), at `about:blank`, held as C10 says. The act starts only with a receiver whose hello's `features` hold
    `act` (C4): the service tests for membership in the list, never for equality, so a receiver with more features has
    the act. With no such receiver, or when the receiver opens no incognito window, the act ends with no window. The window has an incognito browser context of its own. It shares no cookie,
    storage, Cache Storage, service worker, `BroadcastChannel`, HTTP cache or history with the default context, and
    Chrome drops it when its last window closes. The act tab also bypasses service workers
    (`Network.setBypassServiceWorker`).
  - One act context at a time. Before an act the receiver closes an act window that a crash left. The act refuses
    while another incognito window is open.
  - The model marks each act tab, and a popup of an act tab is an act tab. No connection sees an act tab, attaches it
    or gets an event of it. The model keeps every incognito tab (the act's tabs and the operator's private tabs) from
    every client: each event and read that C10 still gives of one (its list N4: `tabs.onCreated`, `tabs.onUpdated`,
    `tabs.onRemoved`, `tabs.onReplaced`, `webNavigation.onCreatedNavigationTarget`, `webNavigation.onErrorOccurred`,
    `downloads.onCreated` and `downloads.onChanged`, the answers of `tabs.get`, `tabs.query`, `windows.get` and
    `debugger.getTargets`, and the act tab's `debugger.onEvent` and `debugger.onDetach`, which carry the typed values)
    goes to the act only, also a `bridge.tabScope` or a `bridge.tooLarge` of one; a download of one never joins a
    client's download; and a window that holds one is in no window lookup. `Target.getTargets` leaves it out; no `Target.targetCreated`, `Target.targetInfoChanged`,
    `Target.targetDestroyed`, `Target.attachedToTarget` or `Target.detachedFromTarget` of it goes to a client; a
    client's `Target.setAutoAttach` attaches nothing of it; and each call with its target id gets
    `No target with given id found`. Its window is in no window lookup: `Browser.getWindowForTarget` with its id gets
    `No target with given id found`, and `Browser.getWindowBounds` and `Browser.setWindowBounds` with its window id get
    `Browser window not found` (the refusals, above). No client's screenshot, recording or close reaches it.
  - The service attaches its own session to the act tab, inside its own process. No socket carries that session. The
    act tab is new: a new document in a new context, with no opener and no window name, and no client has a script, a
    binding or an init script in it.
  - Before the sign-in page loads, the service moves the act window at the X level to the right of the screen's area:
    it gives the act tab's `about:blank` page a title of its own, a new random value for each act that the service
    sets (`aw-act-` and 8 random bytes in hex; the X move takes no title of another form), and moves each X window
    with that title. It types no key until `windows.get` reports the window outside the screen (no pixel of it on the
    screen). An act popup is a tab whose opener is a tab of the act (the `openerTabId` of its `tabs.onCreated`, or
    C10's `webNavigation.onCreatedNavigationTarget` with a tab of the act as its source), or the added tab of an act
    popup's `tabs.onReplaced`; another incognito tab (an operator's private window) is no act popup, and the act moves
    nothing of it. The service attaches its own session to each act popup, with `Fetch` (the guard, below) and
    `Network` (its blocked requests count). An act popup that opens before the password's last key ends the act, so no
    key goes after the service learns of the popup: the act reads that again at once before each key. An act popup
    whose session, `Network` or `Fetch` fails ends the act too, also after the password's last key. An act popup in a
    window of its own moves off the screen by a title of its own in its page, a new random value for each act popup of
    the same form, never by the bounds of a window (`windows.update` refuses an act popup's window); a popup's window
    that is not outside the screen within 2 s ends the act.
  - From the act's start to its end, agentwatch's live view sends no frame of the display to a viewer and plays no
    input from one (C12's `sign_in` event).
  - The fallback. When the incognito window cannot be had, the act can run in a window of the default context, with
    the service-worker bypass, and the model freezes each client tab of the credential's origin during the act
    (`Page.setWebLifecycleState` with `frozen`). An agent's tab of that origin then still shares its storage, Cache
    Storage and `BroadcastChannel` with the act tab, and the Browser pane says so. The fallback is a build decision
    only for that case; stage 1e part 2 (board ab-v16.97.4) builds none: with no incognito window the act ends with no
    window.
- The form rules. The service reads the page only in an isolated world of its own (`Page.createIsolatedWorld`).
  1. The service navigates the act tab to the record's `origin` and `path`. After the load, the main frame's origin
     must be the record's exact origin.
  2. The main frame has exactly one visible, enabled password field. With two or more the act ends. With none and
     exactly one visible username field, the sign-in has two steps (rule 5).
  3. The username field is the visible text, email or tel field before the password field in its form; a field with
     `autocomplete="username"` or `type="email"` comes first. A credential with an empty username skips it.
  4. When the password field is in a `<form>`, the form's method is `post` and its action's origin is in `send_to`.
     This check comes before the first key. A password field with no `<form>` (a sign-in by script) goes on, with the
     block and the guard as its checks.
  5. A sign-in in two steps: the act fills the username, submits, waits for the next page, and applies rules 1 to 4
     again. At most one such step.
  6. The act tab's `Network` domain is on from the navigation of rule 1. At the first key, a WebSocket or a
     WebTransport session of the page to a host outside `send_to` that is still open ends the act.
  7. The type watch. Before the first key, the service puts a `MutationObserver` on the password field's `type`
     attribute in its isolated world. When the type changes, the observer empties the field in its own callback, and
     the act ends.
  - The first build reads only the main frame: a sign-in form in a frame gets the text of no form.
- The fill and the submit.
  - The service takes the input lock of the browser (the input design, section 4.4) for its clicks and keys, and a
    client's input calls wait for it: with the input stage on, the stage's lock; with it off, a step of the activation
    chain, which each client input that starts an action waits for.
  - It clicks each field and types its value with the person's input of the input design: the generator's keys when
    each character has a key on the US layout and the plan fits in 10 s, else `Input.insertText`. The values reach
    Chrome only in the act tab's `Input` calls, over the native link.
  - It submits as a person does: a click on the form's visible submit button, else Enter in the password field.
- The block and the guard.
  - From the first key to the act's end, the receiver holds the act's session rules (C5, rules A to E of the
    receiver's part of the stored sign-ins). They block each request of the act tab, of its popups and of the site's
    workers to a host outside `send_to`, every resource type, the WebSocket included, except a top-level GET. The act
    types no key until the receiver confirms the rules, and the receiver removes them at the act's end, also after a
    failure.
  - The guard. The service keeps `Fetch` on in the act tab and in each act popup that its session holds, for every
    URL, at the request stage. It fails
    (`Fetch.failRequest` with `BlockedByClient`) a request whose URL holds the password, on any origin, and a request
    to an origin outside `send_to` whose body holds the password or whose body Chrome does not give. It looks for the
    password in five forms: plain, URL-encoded, JSON-escaped, base64 and base64url. Every other request continues
    unchanged. A paused request whose event was too large for the link (C10's `bridge.tooLarge`) fails: the guard
    cannot read it.
  - A blocked or failed request does not end the act. No event, prompt, report or log line names its host, because a
    host that the page chooses can carry the password: the `end` event and the act's log line give only the number of
    requests that the block stopped (in the act tab and in each act popup that the service's session holds) and the
    number that the guard stopped. A block of the list rules (C4, C5) in an
    act tab or its popups makes no blocked-site prompt and no blocked report that names its host: the service counts
    it with the requests that the block stopped.
  - Not stopped, stated plainly: a send to an origin of `send_to` (any path, a hash, an encryption, a compression, a
    part of the value, a WebSocket); a service worker's WebSocket to a subdomain or another port of a `send_to` host;
    a top-level GET of an act tab or an act popup to a host on the scope's list with a changed or partial value; the
    requests of an act popup before the service's session holds its `Fetch` (its first navigation among them), so a
    popup that the page opens after the password's last key, or in the moment before the service learns of it, can
    send a GET with the whole value to a host on the scope's list; DNS prefetch and preconnect; and WebRTC.
- The outcome. The act watches the act tab for at most 30 s after the submit.
  - Signed in: the main frame commits a new page or its URL changes, and after 1 s with no navigation the main frame
    has no visible password field. A final host that the scope's list does not cover ends the act (C4 and C5 block
    it); an error page of a blocked navigation, and `about:blank` (where the list's guard sends a page off the list),
    count as such a host.
  - Not accepted: a visible password field is still there after that 1 s.
  - A second factor: a visible field for a code and no password field: `autocomplete="one-time-code"`, or an input
    whose name or id holds `otp`, `totp`, `2fa`, `mfa` or `code` and whose `maxlength` is 4 to 10. The act fills
    nothing there (the answer Q4 a).
  - Timeout: none of these in 30 s.
  - The lockout guard. Three results in a row of not accepted, timeout or a second factor stop the credential, until
    the operator's "Start again" in the Browser pane (C12's `sign_in_start_again`). A signed-in result sets the count to
    zero, and each other result leaves it as it is. At most 6 acts of one credential start in one hour, whatever their
    results. The service keeps the count, the stop and the hour's acts in its state file (C12), so a restart of the
    service does not clear them.
- The clean end and the move, in this order, also after a refusal in the middle of the act:
  1. The service empties each input of the main frame.
  2. Only after signed in: the leak check, then the move. The service reads the act context's cookies of the
     credential's host and its subdomains, and the origin's `localStorage`. The service reads the `localStorage` only
     from a page on the credential's origin; from another origin the move holds no `localStorage` item. When a cookie
     value or a `localStorage` key or value holds the password in one of the five forms, the act makes no move. Else the service builds a C2 payload:
     `domain` the credential's host, `origin` its origin, `url` the origin with the path `/`, the cookies of the host
     and its subdomains, `storage.local` the `localStorage` items, and `storage.session` and `storage.idb` empty. It
     checks the payload as stage 1c checks an import (the C2 rules and the box's own sign-in rule), and gives it to
     the receiver's `import` (C4, C6). This is the import's code path inside the service, not C12's op `import`. C6's
     import closes each tab of the default context whose origin is the credential's origin, and replaces the host's
     cookies.
  3. It clears the tab's history (`Page.resetNavigationHistory`).
  4. It turns `Fetch` off and sends C4's `act_end`: the receiver closes each tab of the act (the act window and its
     popups), then removes the act's rules; the service closes no window itself. Chrome drops the act's context with
     its last window. An act whose `act_rules` failed or came late sends `act_end` too, and so does an act whose
     `windows.create` got no answer in time; an act that opened no window sends none. An `act_end` that fails goes
     once more after 500 ms; after a second failure the service logs it, and the next act window or the receiver's
     start ends the act (C10).
  5. It fills the buffers of the values with zeros, and drops the opened record.
- What the agent sees.
  - Success: the answer `{"signedIn":true,"name":"<name>","origin":"<origin>"}`. The CLI and the MCP tool give the
    text `Signed in to <origin>. Your tabs of this site were closed for the sign-in; open the site again: it loads signed in.`
  - A refusal: the CDP error `{"code":-32000,"message":"Not signed in: <text>"}`, with one text of the table below.
    The CLI prints it and exits with 1, and the MCP tool gives it as its error. The result is the code in C12's `end`
    event and in the log line. `<name>` is the asked name (as a JSON string when it is not a string that matches the
    scope pattern, and `null` for a request with no `name`), `<host>` is the host that the list does not cover, and
    `<origin>` is the record's origin. A link that goes down during the act ends it with the result `not_ready` and

- No text holds a value of the page: a site's own error text can name the username, so the act never passes it on.
  No text names a stop or a start of the agent browser (I2).
- During and after the act.
  - During the act each call on the agent's own tabs works as before, and its input calls wait for the input lock
    while the act types and clicks. The agent's own tabs of the site, in the default context, share nothing with the
    act's context.
  - After the act the move has closed the agent's tabs of the credential's origin. The agent opens them again, and
    they load signed-in pages. The act window, its context and its history are gone.
  - A site that keeps its sign-in in one tab's `sessionStorage` or in IndexedDB gives the agent's tabs no sign-in in
    the first build.
- The log. The service logs one line for each request of `AgentBrowser.signIn`: the user, the scope, the session's
  `repo`, the act id, the credential's id and name, the origin, the result, the time that it took, the number of
  requests that the block stopped and the number that the guard stopped. A refusal by check 1 or 2 names no
  credential. The move logs stage 1c's import line (counts only), and it sends no `error` event: that event is the op
  `import`'s (C12), and the act's `end` event gives the move's result. No log line holds a username, a password, a
  form value, a page's text, a URL path, a query or the host of a request that the block or the guard stopped.
- The limits, stated plainly.
  - The move puts the sign-in's session into the one default context, so each scope whose list covers the host gets
    the signed-in pages (what one profile shares between scopes, above). The answer Q2 decides who may start a
    sign-in, not who rides the session after it.
  - A site's own pages can show the username after the sign-in.
  - A program of the user with the display's X authority can read the display and the act window's title, move the
    window back onto the screen, and send it input.
  - A hostile process of the same OS user can replace the service and wait for the operator's next unlock (the limits
    of the MCP path's admission, above).
