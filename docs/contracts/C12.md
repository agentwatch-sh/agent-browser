# C12. The control door (agent-browser's service <-> the agentwatch daemon)

**The master of C12 (board task ab-v16.94.1).** This file is the master for C12. C12 is new in board task
ab-v16.94.1, stage 0 of the self-contained agent browser. It binds this repository (the service, `agent-browser
service`) and agentwatch (its daemon), and no other. Its source is the design
`docs/superpowers/specs/2026-11-09-self-contained-agent-browser-design.md`, section 7.1: the daemon lead's
proposal and review (R1, R7, m1, C4, C7 and C8), and the operator's answers of 2026-11-10 (its section 19). In
this file C1 to C10 are the contracts of chrome-extension `docs/protocol.md`, and C11 is
`docs/contracts/C11.md`. The vectors: `test/vectors/control.json`.

| Part | Side | From |
| --- | --- | --- |
| The door, its admission, the hello, the service's answers and its events | agent-browser's service | stage 1 (boards ab-v16.94.2 to ab-v16.94.5), off by default |
| The client, the provenance and the requests | the agentwatch daemon | stage 2, off by default |

Nothing uses C12 before stage 1. The old daemon path stays the default, and it does not change, until stage 3
turns the switch on for a box (with the operator's approval). The switch moves the parties of C4 and C10 from
the daemon to the service on that box; C12 is how the daemon then talks to the service.

**The door.**

- A Unix socket with mode 0600, `control.sock`, in the service's run folder (mode 0700):
  `$XDG_RUNTIME_DIR/agent-browser/` on Linux, `~/.cache/agent-browser/run/` on the Mac. A path is at most 103
  bytes. The door has no TCP port.
- One JSON object per line, in UTF-8, with a newline at its end. A line is at most
  `CONTROL_MAX_LINE = 33619968` bytes (the 33,554,432 bytes of a C2 payload and 64 KiB more). A side that reads
  a longer line closes the connection.
- The daemon sends the requests. The service sends the answers and the events. The service sends no request.

**Who connects: only the agentwatch daemon process itself (the daemon lead's R1).** At each accept the service
reads the peer (`SO_PEERCRED` and `SO_PEERPIDFD` on Linux) and admits it only when all of these hold:

1. The service gets the MainPID of agentwatch's unit from the user's systemd at this accept. A daemon restart
   changes it.
2. The peer is the MainPID itself, or a direct child of it: the peer's parent pid is the MainPID, and the
   parent's start time (field 22 of `/proc/<ppid>/stat`) equals the MainPID's start time, read in the same
   check.
3. The peer's command line (`/proc/<pid>/cmdline`) is the daemon's command, which the service's unit file names.
   The command line, not the executable, carries this check: a venv's `python` is a symbolic link, so
   `/proc/<pid>/exe` names the shared interpreter of every Python process.
4. The peer is the same process during the whole check: the service holds its pidfd, and the peer's start time
   is the same before and after the reads, and later than its parent's.

- A process of agentwatch's cgroup is not enough. A child that the daemon forks and that connects itself has
  the daemon, not the MainPID, as its parent, and it is refused. The daemon never passes its connection to
  another process.
- The service's own pid never passes. No agent-browser CLI command is a control client.
- When the check cannot run, the door refuses (the daemon lead's m1). If the systemd query fails, or the daemon
  runs with no systemd user unit, the service sends one line `{"t":"refused","reason":"<text>"}` that gives
  the reason, closes the connection, and logs the reason. The daemon shows that line in `agentwatch health`. The
  service never admits by a weaker rule.
- On the Mac the service reads `LOCAL_PEERPID`, gets the job's pid from `launchctl print gui/<uid>/<agentwatch's label>`
  (its `pid` line) at each accept, reads the parent and the start time with `proc_pidinfo` and the command line
  with `sysctl` (`KERN_PROCARGS2`), and applies the same rules (stage 4; not run on the Mac yet).

**The hello (the daemon lead's C7).** After the admission each side sends its hello as its first line:

- The service: `{"t":"hello","v":1,"side":"service","version":"<agent-browser version>","commit":"<commit or null>","features":[...]}`.
- The daemon: `{"t":"hello","v":1,"side":"daemon","version":"<agentwatch version>","features":[...]}`.

- `v` is the version of this door's lines: 1. `version` is the side's package version. The service's
  `commit` is the 40-hex commit of agent-browser that it runs, or `null` when it cannot tell; the daemon
  compares it with its pin (the design, section 7.3).
- `features` lists the side's additive features. Fields and features are only added, never changed: a side
  ignores a field and a feature that it does not know. A request for an op that the service does not have
  gets `{"t":"res","id":"<id>","ok":false,"error":"unsupported"}`. So an older service and a newer daemon (or
  the reverse) degrade, with no lock-step bump.
- Feature names: `fake` (the hello of `agent-browser service --fake`, a scripted state with no Chrome, for
  agentwatch's hermetic tests). A stage that adds an op or a field adds its feature name to this list first.
- `agent-browser service --hello` prints the service's hello as one line and exits, with no service running.
- The daemon sends no request before it has read the service's hello, and the service answers no request
  before it has read the daemon's hello.

**The lines.**

- A request: `{"t":"req","id":"<id>","op":"<op>","by":{"kind":"<kind>","user":"<user>","via":"<via>"},...}`,
  with the op's fields at the top level, as in C4. `id` is a string, unique on its connection.
- An answer: `{"t":"res","id":"<id>","ok":true,"data":{...}}` or `{"t":"res","id":"<id>","ok":false,"error":"<text>"}`.
  The service answers each request once.
- An event: `{"t":"ev","ev":"<event>",...}`, with the event's fields at the top level.
- A line that is not a JSON object, or a request with no string `id`, closes the connection.
- A request with an op that the service does not have gets `unsupported` (the hello, above).
- A request whose `by` breaks the shape of provenance (below), or whose fields break its row of the requests
  (below), gets `{"t":"res","id":"<id>","ok":false,"error":"bad request"}`.
- A side ignores a line whose `t` it does not know: a newer side can add a kind of line.

**Provenance (the daemon lead's R7).** Each request carries one shape of provenance:
`"by":{"kind":"operator"|"token"|"daemon","user":"<user>","via":"web"|"send"|"cli"|"config"|"daemon"}`.

- `kind: operator` only when the gateway's field is present: the gateway adds
  `"operator":{"user":...,"login":"password"}` to the daemon's op only after its password-login check. The
  daemon refuses a list change, an allow, a dismissal or an import without it. A caller with the API token (an
  agent, or `agentwatch browser ...` in a terminal) never produces it.
- `kind: token` for a start, a stop or a read with the API token (for a start and a stop, today's rule).
- `kind: daemon` for the daemon's own requests: `config`, `set_sessions`, `session_ended`, `launch_check`, and
  the daemon's own reads. `browser.control` is a key of agentwatch's config file, so it comes in `config` with
  `kind: daemon` and `via: config`. The daemon's other own requests have `via: daemon`.
- `user` is the agentwatch user: the login's user for `operator`, the token's user for `token`, and the
  daemon's own user for `daemon`.
- `via` is where the act came from: `web` (the web viewer), `send` (the operator extension's send, C9), `cli`
  (the agentwatch CLI), `config` (the config file), `daemon` (the daemon itself).
- The service checks a request in this order: its op (`unsupported`); the shape of its `by` and its fields
  (`bad request`); then its kind.
- The service applies an operator act (`list_set`, `prompt_allow`, `prompt_dismiss`, `import`) only with
  `kind: operator`; any other kind gets `{"t":"res","id":"<id>","ok":false,"error":"not the operator"}`.
- It applies `start` and `stop` only with `kind: operator` or `kind: token`, and the daemon's own requests
  (`config`, `set_sessions`, `session_ended`, `launch_check`) only with `kind: daemon`; another kind gets
  `bad request`. The reads (`status`, `lists_get`, `prompts_get`, `endpoint`, `sender`) take any kind.
- The service does not check `via`: it logs it.
- The service takes provenance only from the control door, never from a client request (C11), and it logs
  each act with its provenance.

**The requests (daemon to service).**

| Op | Fields | What the service does, and its answer's `data` |
| --- | --- | --- |
| `config` | `enabled`, `control`, `chrome_bin`, `chrome_args`, and agentwatch's other `browser.*` keys | Applies agentwatch's `browser.*` config keys, as data. The daemon sends it at each connect and at each change. `chrome_bin` keeps the way back to Chromium with `--load-extension`; `control: false` makes the endpoint and the MCP path answer their 503 (C11, from stage 3); `enabled: false` stops the browser. `data`: `{}`. |
| `set_sessions` | `sessions` (`[{"scope","repo","roots":[{"pid","start"}],"cgroup"}]`), `remote` (`[{"scope","box","list"}]`, empty until stage 5), `box` (`{"hosts","cookie_names"}`) | A complete snapshot. The service builds the scopes, the list of each scope (by repo), the `set_scopes` object (C4) and the model's roots. No scope object goes out before the first complete snapshot (the daemon lead's C4). `data`: `{}`. |
| `session_ended` | `scope` | Ends the scope: closes its tabs (`end_scope`, the receiver's sweep), drops its roots, removes its list copy, and records the ended scope. `data`: `{}`. |
| `launch_check` | `scope` | Today's `launch_refusal`. `data`: `{"refusal":"<text>"}` while an ended scope of that name is held in memory only, else `{"refusal":null}`. The daemon asks before each launch. If the service does not answer in 2 s, the daemon refuses only a name that ended since its own start, with a text that says to try again. |
| `list_set` (operator) | `list`, `allow` | Checks each entry with the host rules, writes the list file, and the next `set_scopes` carries it. `data`: `{"refused":[{"entry":"<entry>","reason":"<text>"}]}`. |
| `prompt_allow`, `prompt_dismiss` (operator) | `prompt` (the prompt's id) | The service owns the prompts and their dismissals. The allow adds the host to the prompt's list, as a `list_set`, and answers as `list_set` does; the dismissal's `data` is `{}`. A prompt that the service does not know gets the error `this prompt is gone`. |
| `import` (operator, `via: send`) | `payload` (C2) | Checks the payload (C2), drops the box's own sign-in cookies (the hosts and names of `set_sessions`), sends `import` to the receiver (C4), and answers the counts of C4's `import`. Nothing is written to disk. |
| `start`, `stop` (`kind: operator` or `token`) | none | Starts or stops Chrome and Xvfb. Today's rule stays (the API token may start and stop) until the operator answers Q5 (board item ab-6ng). `data`: `{}`. |
| `status` | none | The status: the state (`off`, `starting`, `ready` or `failed closed`), with an agent's text and an operator's text for each state (I2: no agent's text names a stop or a start); Chrome's kind, version, pid and update state, and the extension's version; the endpoint's state (the peer check's form, or why it cannot run); the sessions and lists that the service has; the last stop with its reason and time; the open prompts; the update state. |
| `lists_get`, `prompts_get` | none | The lists and the old single list (read only); the open prompts. |
| `endpoint` | `scope` | The endpoint's URL for the scope (for `agentwatch browser endpoint` and `env`). |
| `sender` | none | The sender's ID, its version and its package (C1, C9). |

Stage 1a fixes the keys of the `data` of `status`, `lists_get`, `prompts_get`, `endpoint` and `sender` in this
table before it builds them, with the daemon lead's review.

The design's table names the prompt's field `id`; here it is `prompt`, because `id` is the request's id. The
design's table names a field `providers` for `list_set` too. No list has providers: the operator chose the
allow prompt, not a list of sign-in providers (board item ab-pbk). So `list_set` has no such field, and a
later rule can add it as an additive field.

**The event stream (service to daemon; the daemon lead's C8).**

| Event | Fields |
| --- | --- |
| `ready` | `chrome_pid`, `chrome_version`, `extension_version`, `endpoint`: the endpoint's state, `{"form":"<form>"}` while the peer check runs (`<form>` is `pidfd`, `stat` or `mac`), or `{"form":null,"reason":"<text>"}` when it cannot run |
| `prompt` | `id`, `state` (`open`, `changed` or `closed`), `host`, `scope`, `list`, `from`, `warnings`; no URL path; the per-host limit of once in 10 s stays |
| `stopped` | `reason`: `receiver_missing`, `sessions_unread`, `start_failed` or `stop`; for `stop`, `by` (the stop's provenance). The daemon sees each fail-closed stop (the daemon lead's C4). |
| `chrome` | `version`, `update` (the update state) |
| `error` | `op`, `user`, `domain`, `counts`; never a page, a cookie or a URL path |

**When the daemon drops (a daemon restart or stop).** The service goes on. Chrome, the endpoint and the last
`set_sessions` stay, and the walk refuses each root that is gone. The event stream keeps no event for a later
reader. At each connect the daemon reads `status`, which gives the state, the last stop with its reason and
time, the open prompts and the update state, so the daemon still sees a `stopped` event that it missed. The
next complete `set_sessions` is the truth again.

**The vectors.** `test/vectors/control.json` holds lines of each kind: the two hellos, a `config`, a
`set_sessions`, operator acts with their provenance, a start with the token, their answers, events, a refused
connection, and lines that break a rule, each with the answer that the service gives.
